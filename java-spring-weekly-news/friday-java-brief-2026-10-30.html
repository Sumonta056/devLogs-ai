Snippet of the week

The MongoDB version of N+1: one lookup per row

A list endpoint loads 100 orders, then calls customers.findById(...) inside the loop. That's 101 round trips. Collect the ids, fetch them all in one $in query, and join in memory.

OrderListService.java · Spring Data MongoDB
record OrderView(String number, String customerName) {}

@Service
class OrderListService {

  private final OrderRepository orders;       // MongoRepository<Order, String>
  private final CustomerRepository customers; // MongoRepository<Customer, String>

  OrderListService(OrderRepository orders, CustomerRepository customers) {
    this.orders = orders;
    this.customers = customers;
  }

  List<OrderView> openOrders() {
    List<Order> list = orders.findByStatus(Status.OPEN);        // query 1

    Set<String> ids = list.stream()
        .map(Order::customerId)
        .collect(Collectors.toSet());

    Map<String, String> names = new HashMap<>();
    customers.findAllById(ids)                                   // query 2: _id $in [...]
        .forEach(c -> names.put(c.id(), c.name()));

    return list.stream()
        .map(o -> new OrderView(o.number(),
            names.getOrDefault(o.customerId(), "(deleted customer)")))
        .toList();
  }
}
// Before: 1 + N queries. After: always 2, however many orders.
Explain like I'm 5

You need milk for 20 friends. You can walk to the shop 20 times, buying one carton each trip, or write one shopping list and go once. Each trip is short, but the walking adds up.

Why it matters

Each query is fast, so no single one shows up in the slow-query log. The cost is round-trip latency multiplied by N. findAllById becomes one query on _id, which is always indexed. Using a Set removes repeated customer ids before the query. For very large lists, page the orders first (that's Week 8's topic).

New Java feature · JDK 25 · JEP 512 · Final

Compact source files and instance main methods

A .java file can now be just methods and fields. The compiler wraps them in an implicit class. main no longer needs public, static or String[] args. The whole java.base module is imported automatically, and the new java.lang.IO class gives you print, println and readln. Final in JDK 25, so no flags are needed.

Fib.java · java Fib.java (JDK 25 or newer)
// Before (JDK 21): the full ceremony
import java.util.List;

public class FibOld {
  public static void main(String[] args) {
    List<Integer> ns = List.of(5, 10, 20);
    for (int n : ns) System.out.println(n + " → " + fib(n));
  }
  static long fib(int n) {
    long a = 0, b = 1;
    for (int i = 0; i < n; i++) { long t = a + b; a = b; b = t; }
    return a;
  }
}

// After (JDK 25+): the whole file, nothing else
void main() {
  for (int n : List.of(5, 10, 20)) {   // List: java.base is auto-imported
    IO.println(n + " → " + fib(n));
  }
}

long fib(int n) {
  long a = 0, b = 1;
  for (int i = 0; i < n; i++) { long t = a + b; a = b; b = t; }
  return a;
}

Explain like I'm 5

Before, writing a two-line note meant filling in a whole official form: name, address, stamp. Now you can just write the note. Java fills in the form for you.

Use it for

Interview practice (this week's Fibonacci in one file), small scripts, quick checks of an API, and teaching. Run with java Fib.java, no separate compile step. When a script grows, add a class declaration and it becomes normal Java again.

Status

Final in JDK 25 (LTS), after previews in JDK 21–24. Not useful inside a Spring Boot app, because an implicit class can't be referenced by other classes. It's for scripts and learning.

Learning path · fetching data, from basic to advanced

Basic → Advanced

Make @ManyToOne lazy

@ManyToOne and @OneToOne default to EAGER, so every query loads the parent too, with extra selects. Write @ManyToOne(fetch = FetchType.LAZY) everywhere, and fetch the association explicitly when a use case needs it.

Fetch what the use case needs

Per query, load the association in the same SQL: @EntityGraph(attributePaths = "customer") on a repository method, or join fetch in JPQL. For read-only lists, a DTO projection selects only the columns you show.

Value classes (JDK 28 preview)

JEP 401 makes value objects without identity. With --enable-preview on JDK 28, Integer and LocalDate become value classes, so == compares values. Preview only, not for production, but run your test suite against an EA build now.

Intermediate · PurchaseOrderRepository.java · Spring Data JPA
public interface PurchaseOrderRepository extends JpaRepository<PurchaseOrder, Long> {

  // Entity + its customer in one SQL (LEFT OUTER JOIN), no @NamedEntityGraph needed
  @EntityGraph(attributePaths = "customer")
  List<PurchaseOrder> findByStatus(Status status);

  // Read-only list: select just two columns into a record
  @Query("""
      select new com.example.shop.OrderSummary(o.number, c.name)
      from PurchaseOrder o join o.customer c
      where o.status = :status
      """)
  List<OrderSummary> findSummaries(@Param("status") Status status);
}

Tips & tricks

  1. T1

    Turn off Open Session in View

    spring.jpa.open-in-view is true by default (Boot logs a warning about it). It keeps the session open while JSON is written, so lazy loads in the controller or serializer quietly run extra queries. Set it to false and they fail fast with LazyInitializationException instead.

  2. T2

    A safety net: batch fetching

    spring.jpa.properties.hibernate.default_batch_fetch_size=50 makes Hibernate load lazy associations for up to 50 parents with one IN (...) query. 200 lazy loads become 4 queries. It's a net, not a fix: still fetch what each use case needs.

  3. T3

    Count statements in tests

    In a test profile, set spring.jpa.properties.hibernate.generate_statistics=true, then read entityManagerFactory.unwrap(SessionFactory.class).getStatistics().getPrepareStatementCount() before and after a call. Assert the difference, so a new N+1 breaks the build.

  4. T4

    MongoDB @DBRef has the same trap

    Each @DBRef on a document is resolved with its own query when the document is read (or on first access if lazy = true). A list of 100 orders with a @DBRef customer means up to 100 extra queries. For list endpoints, store the id and batch with findAllById, as in the snippet.

  5. T5

    Rebuild native images after a trust-store fix

    Both eMudhra fixes change the JDK's CA certificates. A GraalVM native image keeps the trust store from build time, so updating the JDK on the build machine isn't enough: rebuild and redeploy the image.

Industry & interview questions

Interview Q&A

BasicWhat is the N+1 query problem?

You run one query to load N rows, then the code triggers one more query per row to load something related, for example each order's customer. That's N+1 queries where 1 or 2 would do. Each query is fast, so it rarely shows up in the slow-query log, but the round trips add up and grow with the data.

It happens with lazy associations accessed in a loop, with EAGER associations loaded by a JPQL query that doesn't fetch them, and in MongoDB with per-row lookups or @DBRef.

Midjoin fetch, @EntityGraph or batch fetching: when do you use which?

join fetch in JPQL gives full control and works with a custom where. @EntityGraph(attributePaths = ...) does the same for derived query methods without writing JPQL. Both load the association in the same SQL.

Batch fetching (default_batch_fetch_size or @BatchSize) keeps the association lazy but loads it for many parents with one IN query. Use it for collections on paged results, where fetch-joining a collection would make Hibernate paginate in memory.

MidWhy does the naive recursive Fibonacci get so slow?

Each call makes two more calls, and the same values are computed again and again. fib(40) makes 331,160,281 calls (that's 2 × fib(41) − 1). Time grows exponentially, about 1.618n. Memoization stores each result once, so it's O(n). The loop needs only the last two values, so it's O(n) time and O(1) space with no stack depth risk.

SeniorHow do you stop N+1 regressions across a team?

Make them visible and make them fail. Turn off Open Session in View so lazy loads outside a transaction throw. Make @ManyToOne lazy by convention. Add statement-count assertions to integration tests for list endpoints (Hibernate statistics, or Vlad Mihalcea's Hypersistence Utils). In production, watch queries per request in your tracing, since a page that issues 300 fast queries still looks healthy in the slow-query log.

Design-wise, prefer DTO projections for read-only lists and keep entity graphs per use case, not one global EAGER setting.

Fibonacci three ways

  • Write long fibRecursive(int n), long fibMemo(int n) and long fibIterative(int n), with fib(0) = 0 and fib(1) = 1.
  • Throw IllegalArgumentException for n < 0. fib(92) is the largest that fits in a long, so fibMemo and fibIterative must throw ArithmeticException on overflow instead of returning a wrong number.
  • State the time and space of each version.
Expected
fibIterative(0)    // 0
fibIterative(1)    // 1
fibIterative(10)   // 55
fibRecursive(40)   // 102334155  (noticeably slow)
fibMemo(50)        // 12586269025
fibIterative(92)   // 7540113804746346429
fibIterative(93)   // ArithmeticException: long overflow
Show solution
Fib.java
import java.util.Arrays;

public class Fib {

  // 1. Plain recursion: O(1.618^n) time, O(n) stack
  public static long fibRecursive(int n) {
    if (n < 0) throw new IllegalArgumentException("n must be >= 0");
    if (n < 2) return n;
    return fibRecursive(n - 1) + fibRecursive(n - 2);
  }

  // 2. Memoized recursion: O(n) time, O(n) space
  public static long fibMemo(int n) {
    if (n < 0) throw new IllegalArgumentException("n must be >= 0");
    long[] memo = new long[n + 1];
    Arrays.fill(memo, -1);               // -1 = not computed yet
    return fibMemo(n, memo);
  }

  private static long fibMemo(int n, long[] memo) {
    if (n < 2) return n;
    if (memo[n] != -1) return memo[n];
    memo[n] = Math.addExact(fibMemo(n - 1, memo), fibMemo(n - 2, memo));
    return memo[n];
  }

  // 3. Loop: O(n) time, O(1) space
  public static long fibIterative(int n) {
    if (n < 0) throw new IllegalArgumentException("n must be >= 0");
    if (n == 0) return 0;
    long prev = 0, curr = 1;
    for (int i = 2; i <= n; i++) {
      long next = Math.addExact(prev, curr); // throws on overflow
      prev = curr;
      curr = next;
    }
    return curr;
  }

  public static void main(String[] args) {
    System.out.println(fibIterative(10));  // 55
    System.out.println(fibRecursive(40));  // 102334155
    System.out.println(fibMemo(50));       // 12586269025
    System.out.println(fibIterative(92));  // 7540113804746346429
    fibIterative(93);                      // ArithmeticException: long overflow
  }
}

How it works. The recursive version recomputes the same values: fib(40) makes 331,160,281 calls. The memo array stores each answer the first time, so every n is computed once. The loop keeps only the last two numbers. Math.addExact turns a silent overflow at fib(93) into an exception.

Recursive: Time O(φ^n) · Space O(n)Memo: Time O(n) · Space O(n)Loop: Time O(n) · Space O(1)

Follow-up they'll ask. "Why not memoize with map.computeIfAbsent(n, k -> fib(k - 1) + fib(k - 2))?" Because the function changes the same HashMap while it runs, and since Java 9 HashMap.computeIfAbsent throws ConcurrentModificationException when it detects that. Use an array or a plain get/put. Also: "fib(1000)?" Switch to BigInteger. "Faster than O(n)?" Fast doubling or matrix power gives O(log n).

The open-orders page runs 151 queries

  • There are 200 open orders from 150 different customers. Calling the endpoint runs 151 SQL statements. Explain where they come from and why it's 151, not 201.
  • Fix it so the endpoint runs one statement, and make customer lazy.
  • Add a test that fails if someone brings the N+1 back.
Buggy code
@Entity
public class PurchaseOrder {
  @Id @GeneratedValue private Long id;
  private String number;
  @Enumerated(EnumType.STRING) private Status status;
  @ManyToOne private Customer customer;
  // getters ...
}

public interface PurchaseOrderRepository extends JpaRepository<PurchaseOrder, Long> {
  @Query("select o from PurchaseOrder o where o.status = :status")
  List<PurchaseOrder> findByStatus(@Param("status") Status status);
}

public record OrderSummary(String number, String customerName) {}

@RestController
class OrderController {
  private final PurchaseOrderRepository orders;
  OrderController(PurchaseOrderRepository orders) { this.orders = orders; }

  @GetMapping("/api/orders/open")
  List<OrderSummary> open() {
    return orders.findByStatus(Status.OPEN).stream()
        .map(o -> new OrderSummary(o.getNumber(), o.getCustomer().getName()))
        .toList();
  }
}
Show solution

Where the queries come from. @ManyToOne is EAGER by default. The JPQL query selects only orders (statement 1), so Hibernate then loads each order's customer with a separate select. Hibernate keeps loaded entities in the persistence context, so each distinct customer is loaded once: 1 + 150 = 151. With all 200 orders from different customers it would be 201. Switching to LAZY alone doesn't help: the selects just move into the .map(...) loop (and, with Open Session in View on, nobody notices).

Fixed: entity, repository, OrderQueryCountTest.java
// 1. Entity: lazy by default
@ManyToOne(fetch = FetchType.LAZY)
private Customer customer;

// 2. Repository: fetch the customer in the same SQL when this use case needs it
public interface PurchaseOrderRepository extends JpaRepository<PurchaseOrder, Long> {

  @Query("select o from PurchaseOrder o join fetch o.customer where o.status = :status")
  List<PurchaseOrder> findByStatus(@Param("status") Status status);

  // Alternative for this read-only page: select only the two columns
  @Query("""
      select new com.example.shop.OrderSummary(o.number, c.name)
      from PurchaseOrder o join o.customer c
      where o.status = :status
      """)
  List<OrderSummary> findSummaries(@Param("status") Status status);
}

// 3. Guard test (assumes test data with several open orders)
@SpringBootTest(properties = {
    "spring.jpa.properties.hibernate.generate_statistics=true",
    "spring.jpa.open-in-view=false" })
class OrderQueryCountTest {

  @Autowired EntityManagerFactory emf;
  @Autowired OrderController controller;

  @Test
  void openOrdersRunOneStatement() {
    Statistics stats = emf.unwrap(SessionFactory.class).getStatistics();
    stats.clear();

    List<OrderSummary> result = controller.open();

    assertThat(result).isNotEmpty();
    assertThat(stats.getPrepareStatementCount()).isEqualTo(1);
  }
}

How it works. join fetch tells Hibernate to load each order's customer in the same SQL with an inner join, so the loop reads data that's already in memory. The DTO version is even lighter: no entities, no persistence context, just two columns. @EntityGraph(attributePaths = "customer") on a derived method does the same as join fetch (with a left outer join). The test reads Hibernate's statement counter, so the build turns red if a lazy load sneaks back in.

Follow-up they'll ask. "Now the page also shows order lines, and it's paged." Don't join fetch a collection together with Pageable: Hibernate can't limit rows in SQL then, so it loads everything and pages in memory, with a warning. Page the order ids first, then fetch the lines for those ids, or set spring.jpa.properties.hibernate.default_batch_fetch_size so the lines load in a few IN queries.

Best practices · Industry practices

Do this, avoid that

Do

  • Map every @ManyToOne and @OneToOne as LAZY, and fetch associations per use case with join fetch or @EntityGraph.
  • Use DTO projections (records) for read-only list pages.
  • Batch MongoDB lookups with findAllById (one $in query) instead of findById in a loop.
  • Assert SQL statement counts in integration tests for list endpoints.
  • Update JDKs and rebuild native images after both eMudhra fixes (21 and 24 Oct).

Avoid

  • Leaving spring.jpa.open-in-view on. It hides lazy loading until production traffic finds it.
  • join fetch on a collection together with Pageable. Hibernate pages in memory.
  • Switching to EAGER to "fix" a LazyInitializationException. It makes every query heavier.
  • HashMap.computeIfAbsent with a recursive function. It throws ConcurrentModificationException.
  • Relying on value-class (==) behaviour from the JDK 28 preview in production code.

Real problem, solved with data

"31 extra queries to show 15 exchange rates"

Problem. A Spring Boot service listed exchange rates. Each ExternalExchangeRate has two lazy @ManyToOne links, currencyFrom and currencyTo. The code looped over the rates and read both currency codes.

Diagnosis. With SQL logging and Hibernate statistics turned on in the dev profile, the endpoint showed 33 prepared statements and 31 entities fetched one at a time: the SQL log was full of select ... from currencies where id = ?.

2
Response · before
48 ms

Fix. Add LEFT JOIN FETCH e.currencyFrom LEFT JOIN FETCH e.currencyTo to the repository queries, with a separate countQuery for paged methods. The author applied it to 48 methods across 7 modules. Statements went from 33 to 2: (33 − 2) ÷ 33 ≈ 94% fewer. Response time went from 48 to 37 ms: 11 ÷ 48 ≈ 23% faster. Statement prepare time went from about 413 to 61 µs: 352 ÷ 413 ≈ 85% less.

Real numbers from Taras Antoniuk, "How JOIN FETCH Reduced Database Load by 94%: A Real-World Case Study" (DEV Community, 15 Dec 2025). Measured with 15 records on a local PostgreSQL, so the time savings will be bigger with more rows and a remote database; the article's 1,000-row figures are estimates, not measurements. "Database load" here means statement count.
