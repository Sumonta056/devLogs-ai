Snippet of the week

Atomic order numbers in MongoDB with findAndModify

Need human-friendly IDs like ORD-000042 that never repeat, even with three app instances running? One atomic MongoDB operation increments a counter and hands you the new value.

OrderNumberService.java · Spring Data MongoDB
@Document("counters")
record Counter(@Id String id, long seq) {}

@Service
class OrderNumberService {

  private final MongoTemplate mongo;
  OrderNumberService(MongoTemplate mongo) { this.mongo = mongo; }

  String next() {
    Counter c = mongo.findAndModify(
        Query.query(Criteria.where("_id").is("order")),
        new Update().inc("seq", 1),
        FindAndModifyOptions.options().returnNew(true).upsert(true),
        Counter.class);
    return "ORD-%06d".formatted(c.seq());
  }
}

// First call creates {_id: "order", seq: 1} → "ORD-000001"
// Every later call: +1, atomically, on the server
Explain like I'm 5

A bakery has one ticket machine by the door. Each customer pulls a ticket, and the machine prints the next number.

Two people can't get the same number, because the machine does "add one and print" as a single click. MongoDB is that machine: $inc and "give me the new value" happen in one step.

Why it matters

The common mistake is read, add one in Java, then save. Two requests read 41 at the same moment and both save 42. returnNew(true) gives you the value after the update; upsert(true) creates the counter on first use. It looks up by _id, which is always indexed, so no extra index is needed.

New Java feature · JDK 25 · JEP 513 · Final

Flexible Constructor Bodies: code before super(...)

Since JDK 25 a constructor can run statements before it calls super(...) or this(...). You can validate arguments and assign your own fields there. You still can't use this, call instance methods or read fields in that "prologue". Fully final, so no preview flags.

Taka.java · javac --release 25 (or newer)
class Money {
  Money(long minorUnits, String currency) { /* ... */ }
}

// Before (JDK 21): checks had to hide in a static helper
class TakaOld extends Money {
  TakaOld(long paisa) {
    super(requireNonNegative(paisa), "BDT");
  }
  private static long requireNonNegative(long v) {
    if (v < 0) throw new IllegalArgumentException("negative");
    return v;
  }
}

// After (JDK 25+): validate first, then call super
class Taka extends Money {
  private final String label;
  Taka(long paisa, String label) {
    if (paisa < 0) throw new IllegalArgumentException("negative");
    this.label = label;  // allowed: assigning my own field
    super(paisa, "BDT");
  }
}
Explain like I'm 5

Before building a house, you check the bricks. The old rule said: pour the foundation first, then check the bricks. The new rule lets you check first and stop early if the bricks are broken.

Use it for

Argument checks before an expensive parent constructor runs. It also fixes a classic bug: a parent constructor calls an overridden method that reads a child field which isn't set yet (it prints null). Assign the field before super() and the parent sees the real value.

Status

Final in JDK 25 (LTS) and later. Spring Boot 4.1 runs on Java 17–26, so you can use it when your service runs on JDK 25+.

Learning path · configuration, from basic to advanced

Basic → Advanced

Profile-specific files

application-dev.yaml and application-prod.yaml override application.yaml when that profile is active. Activate with --spring.profiles.active=prod or the SPRING_PROFILES_ACTIVE env var.

Typed config records

Bind a prefix to a record and let Boot convert units: "30s" becomes a Duration, "10MB" a DataSize. Add @Validated so bad config fails at startup, not at 2 a.m.

JDK's own JSON API

JEP 540 is targeted to JDK 28 as an incubator (--add-modules jdk.incubator.json). Good for small tools and scripts without Jackson. The API can still change, so not for production.

Tips & tricks

  1. T1

    MongoDB properties moved in Boot 4

    Connection settings are now spring.mongodb.*: spring.mongodb.uri, spring.mongodb.database, spring.mongodb.ssl.bundle. Spring Data settings stay put: spring.data.mongodb.auto-index-creation, spring.data.mongodb.field-naming-strategy. An old spring.data.mongodb.uri line can leave you connecting to localhost.

  2. T2

    Never put spring.profiles.active in a profile file

    It is only allowed in non-profile-specific documents. Inside application-prod.yaml or an on-profile block, Boot rejects it at startup. The same rule applies to spring.profiles.include and spring.profiles.group.

  3. T3

    Group profiles instead of listing five

    spring.profiles.group.production[0]=proddb and [1]=prodmq, then --spring.profiles.active=production turns on all three.

  4. T4

    Get autocomplete for your own properties

    Add org.springframework.boot:spring-boot-configuration-processor as an annotation processor. IntelliJ then completes and documents app.* keys from your @ConfigurationProperties records.

  5. T5

    Put Spring upgrades on the calendar

    With "Patch Thursday", every Spring patch now lands on one day a month. Book a dependency-bump PR for the Friday after: next one is 23 Oct, the day after the 22 Oct train.

Industry & interview questions

Interview Q&A

BasicWhat is a Spring profile, and how do you activate one?

A named set of config and beans for one environment (dev, test, prod). Boot loads application-{profile}.yaml on top of application.yaml, and beans marked @Profile("prod") are only created when prod is active.

Activate with --spring.profiles.active=prod, SPRING_PROFILES_ACTIVE=prod, or in tests with @ActiveProfiles("test"). With no active profile, the profile called default is used.

Mid@Value or @ConfigurationProperties: which and why?

@Value("${app.x}") is fine for one value. For a group of settings, @ConfigurationProperties wins: it is type-safe, supports relaxed binding (max-upload, MAX_UPLOAD), nested objects, lists, unit conversion and @Validated, and gives IDE metadata. A record makes the config immutable.

MidIf two profiles set the same property, which value wins?

Profile-specific files always override application.yaml. Between active profiles it's last-wins: with spring.profiles.active=prod,live, application-live overrides application-prod. Command-line args and environment variables still beat all of these files.

SeniorHow do you handle secrets across dev, staging and prod?

Keep them out of Git entirely. application.yaml holds safe defaults; real secrets come from environment variables (relaxed binding maps SPRING_MONGODB_URI to spring.mongodb.uri), mounted config trees (spring.config.import=configtree:/run/secrets/) or a vault. Validate them with @Validated so a missing secret stops the app at startup, and never log the bound properties object.

Java · Week 2Easy

Are these two strings anagrams?

  • Write boolean isAnagram(String a, String b).
  • Ignore case and spaces. Inputs contain only English letters and spaces.
  • Don't sort. Aim for O(n) time and O(1) extra space.
Expected
isAnagram("listen", "silent")          // true
isAnagram("Dormitory", "Dirty room")  // true
isAnagram("rat", "car")                // false
isAnagram("aab", "abb")                // false
Show solution
Anagram.java
public static boolean isAnagram(String a, String b) {
  int[] count = new int[26];
  for (int i = 0; i < a.length(); i++) {
    char c = a.charAt(i);
    if (c != ' ') count[Character.toLowerCase(c) - 'a']++;
  }
  for (int i = 0; i < b.length(); i++) {
    char c = b.charAt(i);
    if (c != ' ') count[Character.toLowerCase(c) - 'a']--;
  }
  for (int n : count) {
    if (n != 0) return false;
  }
  return true;
}

How it works. One counter per letter. Letters in a add one, letters in b subtract one. If every counter ends at zero, both strings used exactly the same letters the same number of times.

Time O(n + m)Space O(1)

Follow-up they'll ask. What about Unicode, like Bangla text? The 26-slot array breaks. Count code points in a HashMap<Integer, Integer> using a.codePoints() and map.merge(cp, 1, Integer::sum). Also mention the sort-and-compare version (Arrays.sort on both char arrays): simpler, but O(n log n).

Spring Boot · Week 2Medium

Fix the config that won't start

  • This Boot 4 app fails at startup. Name both problems.
  • Fix them so prod uses its own values when started with that profile.
  • Add checks: page-size must be 1–100 and supplier-url is required.
Buggy code
@ConfigurationProperties("app.catalog")
public record CatalogProperties(
    int pageSize, Duration cacheTtl, String supplierUrl) {}

@Service
class CatalogService {
  CatalogService(CatalogProperties props) { /* ... */ }
}

@SpringBootApplication
public class ShopApplication { /* main(...) */ }

# application-prod.yaml
spring:
  profiles:
    active: prod
app:
  catalog:
    page-size: 50
    cache-ttl: 30m
    supplier-url: https://supplier.example.com
Show solution

Problem 1. The record is never registered as a bean. @ConfigurationProperties alone doesn't create one, so startup fails because CatalogService needs a CatalogProperties bean that doesn't exist. Problem 2. spring.profiles.active inside a profile-specific file is invalid, and Boot rejects it at startup. A file can't switch on the profile that loads it.

Fixed: ShopApplication.java, CatalogProperties.java, YAML
@SpringBootApplication
@ConfigurationPropertiesScan          // registers every @ConfigurationProperties type
public class ShopApplication {
  public static void main(String[] args) {
    SpringApplication.run(ShopApplication.class, args);
  }
}

@Validated                            // needs spring-boot-starter-validation
@ConfigurationProperties("app.catalog")
public record CatalogProperties(
    @Min(1) @Max(100) @DefaultValue("20") int pageSize,
    @DefaultValue("5m") Duration cacheTtl,
    @NotBlank String supplierUrl) {}

# application.yaml (defaults, used in dev)
app:
  catalog:
    supplier-url: http://localhost:8081

# application-prod.yaml (no spring.profiles.active here)
app:
  catalog:
    page-size: 50
    cache-ttl: 30m
    supplier-url: https://supplier.example.com

# Start prod with:  java -jar shop.jar --spring.profiles.active=prod
# or set env var:   SPRING_PROFILES_ACTIVE=prod

How it works. @ConfigurationPropertiesScan finds the record and binds it through its constructor (no @ConstructorBinding needed for a record with one constructor). @DefaultValue fills missing keys, and "30m" converts to a Duration. If prod sets page-size: 500, @Validated stops startup with a clear binding error.

Alternative. @EnableConfigurationProperties(CatalogProperties.class) on any @Configuration class registers just that one type.

Follow-up they'll ask. Why not put @Component on the record? The docs say constructor binding doesn't work for beans created by component scanning, @Bean methods or @Import. Use the scan or @EnableConfigurationProperties.

Best practices · Industry practices

Do this, avoid that

Do

  • Group related settings into one @Validated @ConfigurationProperties record per feature.
  • Keep application.yaml runnable for local dev, and put only the differences in application-prod.yaml.
  • Use typed values: Duration for timeouts, DataSize for limits, not int timeoutMs.
  • Use atomic MongoDB updates ($inc, findAndModify) for counters and stock levels.
  • Track Spring's monthly patch day and upgrade within a week of it.

Avoid

  • Committing passwords or connection strings to application-prod.yaml.
  • Branching on if (env.equals("prod")) in code. Use config values or @Profile beans.
  • Read-modify-write in Java for counters. Two requests will read the same value.
  • Keeping spring.data.mongodb.uri after moving to Boot 4. It's spring.mongodb.uri now.
  • Shipping incubator APIs (jdk.incubator.json) in production services.

Real problem, solved with data

"Copying a HashMap was the slow part"

Problem. new HashMap<>(other) and putAll(other) are everywhere in Java services: copying request headers, building a response, taking a snapshot of a cache. Before JDK 27 they went through the generic Map path even when the source was itself a HashMap.

Diagnosis. Oracle's JDK engineers benchmarked these calls and found the generic path doing work a HashMap-to-HashMap copy doesn't need. They found similar waste in file opening (redundant system calls) and AES/ECB encryption.

HashMap copy · before
10,593 ns
HashMap copy · after
1,533 ns
File open · before
3,722 ns
File open · after
3,192 ns
AES/ECB · before
11.52 µs
AES/ECB · after
8.38 µs

Fix. JDK 27 added a special path for HashMap sources. In that benchmark the copy takes 1,533 ÷ 10,593 ≈ 14.5% of the old time: 85.5% less, or about 6.9× faster. File open went from 3,722 to 3,192 ns (14.2% less). AES/ECB went from 11.52 to 8.38 µs, which is 11.52 ÷ 8.38 ≈ 1.37×, the reported 37% throughput gain. Your fix: upgrade the JDK. You don't change any code.

Real numbers from Oracle's "Performance Improvements in JDK 27" (Inside.java, 28 Sep 2026). The post reports a 61–86% range for the HashMap change, and this is its headline benchmark. Micro-benchmarks don't predict end-to-end gains, so measure your own service before and after.
