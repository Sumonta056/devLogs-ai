Snippet of the week

Self-deleting documents with a MongoDB TTL index

Password-reset tokens, OTP codes and idempotency keys should disappear on their own. A TTL index makes MongoDB delete each document a fixed time after the date in one field, so you don't need a cleanup job.

ResetTokens.java · Spring Data MongoDB
@Document("password_reset_tokens")
record ResetToken(@Id String token, String userId, Instant createdAt) {}

@Configuration
class ResetTokenIndexes {

  // Runs once at startup; does nothing if the index already exists
  @Bean
  ApplicationRunner resetTokenTtl(MongoTemplate mongo) {
    return args -> mongo.indexOps(ResetToken.class)
        .ensureIndex(new Index()
            .on("createdAt", Sort.Direction.ASC)
            .expire(Duration.ofMinutes(15)));
  }
}

// Save with: new ResetToken(uuid, userId, Instant.now())
// About 15 minutes later MongoDB removes it by itself
Explain like I'm 5

Each token gets a sticker with the time it was made. A cleaner walks past now and then and throws away anything whose sticker is older than 15 minutes.

Why it matters

The index only works on a BSON date field (a Java Instant is stored as one), and it must be a single-field index. Deletion isn't instant, because a background thread does the cleanup. So also check createdAt in code when you validate a token. Spring Data doesn't create indexes from annotations unless spring.data.mongodb.auto-index-creation=true, which is why this snippet creates the index explicitly.

New Java feature · JDK 27 · JEP 533 · Preview (final proposed in JEP 543)

Structured concurrency: run calls in parallel as one unit

StructuredTaskScope forks subtasks (each on a virtual thread by default) and treats them as one unit. If one fails, the others are cancelled, and no thread outlives the try block. In JDK 27, join() throws a checked ExecutionException that wraps the first failure.

OrderPage.java · javac --release 27 --enable-preview
// Before: a thread pool and two futures. If the customer call
// fails, the order call keeps running and nobody cancels it.
OrderPage loadOld(String id) throws Exception {
  Future<Order> order = pool.submit(() -> orders.find(id));
  Future<Customer> cust = pool.submit(() -> customers.forOrder(id));
  return new OrderPage(order.get(), cust.get());
}

// After (JDK 27 preview): one scope owns both calls
import java.util.concurrent.StructuredTaskScope;
import java.util.concurrent.StructuredTaskScope.Subtask;

OrderPage load(String id)
    throws InterruptedException, ExecutionException {
  try (var scope = StructuredTaskScope.open()) {
    Subtask<Order> order = scope.fork(() -> orders.find(id));
    Subtask<Customer> cust = scope.fork(() -> customers.forOrder(id));

    scope.join();  // one fails → the other is cancelled

    return new OrderPage(order.get(), cust.get());
  }               // close(): no thread left behind
}

// Run: java --enable-preview OrderPage.java
Explain like I'm 5

You send two friends to buy bread and milk. With the old way, if the bread shop is closed, the milk friend keeps walking anyway. With a scope, you're holding both their hands. If one stops, you call the other one back, and nobody goes home alone.

Use it for

An endpoint that calls two or three services or MongoDB queries at once and needs all the results. Use StructuredTaskScope.open(Joiner.anySuccessfulOrThrow()) when the first good answer is enough, like calling two mirrors of one service.

Status

Seventh preview in JDK 27 (needs --enable-preview, and only compiles on JDK 27). JEP 543 proposes making it final in JDK 28 with no changes. Learn it now, but wait for JDK 28 before production use.

Learning path · request validation, from basic to advanced

Basic → Advanced

Constraints + @Valid

Put @NotBlank, @Email and @Min on record components, add spring-boot-starter-validation, and mark the body @Valid @RequestBody. Failures become a 400 before your code runs.

Your own constraint

When no built-in annotation fits (a Bangladeshi mobile number, an SKU format), write an annotation plus a ConstraintValidator. It works on fields, parameters and list elements.

Method validation

Constraints directly on controller parameters (@PathVariable @Min(1) long id) use Spring's built-in method validation and raise HandlerMethodValidationException. Remove class-level @Validated from controllers to use it.

Intermediate · BdMobile.java + BdMobileValidator.java
@Documented
@Constraint(validatedBy = BdMobileValidator.class)
@Target({ElementType.FIELD, ElementType.PARAMETER, ElementType.TYPE_USE})
@Retention(RetentionPolicy.RUNTIME)
public @interface BdMobile {
  String message() default "must be a Bangladeshi mobile number, e.g. 01712345678";
  Class<?>[] groups() default {};
  Class<? extends Payload>[] payload() default {};
}

public class BdMobileValidator implements ConstraintValidator<BdMobile, String> {
  // 01XXXXXXXXX or +8801XXXXXXXXX; the digit after "1" is 3–9
  private static final Pattern MOBILE = Pattern.compile("^(?:\\+?880|0)1[3-9]\\d{8}$");

  @Override
  public boolean isValid(String value, ConstraintValidatorContext ctx) {
    return value == null || MOBILE.matcher(value).matches(); // null → let @NotBlank decide
  }
}

// Use it: record SignupRequest(@NotBlank @BdMobile String phone) {}

Tips & tricks

  1. T1

    Turn on RFC 9457 error bodies with one property

    spring.mvc.problemdetails.enabled=true makes Boot register a ResponseEntityExceptionHandler, so built-in errors (validation, 405, 415 and so on) come back as application/problem+json. If you write your own advice for one of those exceptions, it must be ordered ahead of Boot's handler.

  2. T2

    Validate list elements, not just the list

    @NotEmpty List<OrderLine> lines only checks the list. Write @NotEmpty List<@Valid OrderLine> lines to check every line, or List<@NotBlank String> tags for simple values.

  3. T3

    Handle both validation exceptions

    @Valid on a body raises MethodArgumentNotValidException. A constraint directly on a parameter (@RequestParam @Max(100) int size) switches the method to method validation and raises HandlerMethodValidationException. Spring's docs say to handle both.

  4. T4

    MongoDB indexes aren't created for you

    spring.data.mongodb.auto-index-creation is off by default, so @Indexed does nothing on its own. Turn it on for small apps, or create indexes explicitly with mongoTemplate.indexOps(Type.class).ensureIndex(...) as in the snippet above.

  5. T5

    Customize the default validation message

    Spring resolves the problem-detail message code problemDetail.org.springframework.web.bind.MethodArgumentNotValidException from messages.properties. Argument {1} is the list of field errors, e.g. ...=Request validation failed: {1}.

Industry & interview questions

Interview Q&A

Basic@Valid or @Validated: what's the difference?

@Valid is the standard Jakarta Bean Validation annotation. It validates an object and cascades into nested fields marked @Valid. @Validated is Spring's version. It also accepts validation groups (@Validated(OnCreate.class)), and on a class it turns on method validation through an AOP proxy, for example on a @Service.

On a @RequestBody parameter both work. Use @Valid unless you need groups.

MidWhy does a request with a blank name still get saved?

The usual causes: no @Valid on the @RequestBody parameter; spring-boot-starter-validation isn't on the classpath, so there's no validator; the constraint is on a nested object or list element without @Valid to cascade; or the parameter has a BindingResult right after it, so errors are handed to your method and nobody checks them.

MidWhat are the rules and limits of a MongoDB TTL index?

It's a single-field index (compound indexes can't have a TTL) on a BSON date, or an array of dates, in which case the oldest date counts. A document expires expireAfterSeconds after the date in that field. With a value of 0, the field itself is the expiry time. Deletion is done by a background thread, so expired documents can still be read for a short time. You can change the time on an existing index with collMod.

SeniorStructured concurrency vs CompletableFuture: when do you pick which?

CompletableFuture is good for async pipelines and callbacks, but its tasks have no owner. If one fails, the others keep running unless you cancel them yourself, and a thread dump doesn't show which request started them. A StructuredTaskScope ties subtasks to a block of code: failure cancels the siblings, close() waits for every thread to finish, and thread dumps show the parent-child tree.

Since each subtask is a blocking call on a virtual thread, the code reads top to bottom. Today it's preview in JDK 27 (JEP 533), proposed final for JDK 28 (JEP 543). For production on JDK 21/25, use CompletableFuture or a virtual-thread executor.

Find the duplicates in an array

  • Write List<Integer> findDuplicates(int[] nums).
  • Return every value that appears more than once, each only once, in the order it was first repeated.
  • Don't sort or change the input. Aim for O(n) time.
Expected
findDuplicates(new int[]{4, 3, 2, 7, 8, 2, 3, 1})  // [2, 3]
findDuplicates(new int[]{3, 1, 3, 1, 2})           // [3, 1]
findDuplicates(new int[]{5, 5, 5, 5})              // [5]
findDuplicates(new int[]{1, 2, 3})                 // []
findDuplicates(new int[]{})                        // []
Show solution
Duplicates.java
import java.util.*;

public class Duplicates {

  public static List<Integer> findDuplicates(int[] nums) {
    Set<Integer> seen = new HashSet<>();
    Set<Integer> dups = new LinkedHashSet<>(); // keeps insertion order
    for (int n : nums) {
      if (!seen.add(n)) {   // add() returns false if n was already there
        dups.add(n);         // a Set, so 5,5,5,5 reports 5 once
      }
    }
    return new ArrayList<>(dups);
  }

  public static void main(String[] args) {
    System.out.println(findDuplicates(new int[]{4, 3, 2, 7, 8, 2, 3, 1})); // [2, 3]
    System.out.println(findDuplicates(new int[]{3, 1, 3, 1, 2}));          // [3, 1]
    System.out.println(findDuplicates(new int[]{5, 5, 5, 5}));             // [5]
  }
}

How it works. Set.add returns false when the value is already present, so one call both checks and records. The first time a value fails add, it's a duplicate. Putting it in a LinkedHashSet removes repeats and keeps the order they were found in.

Time O(n)Space O(n)

Follow-up they'll ask. "Values are 1..n and you may change the array. Use O(1) extra space." Walk the array, and for each value v flip the sign of nums[|v| - 1]. If it's already negative, |v| is a duplicate. They may also ask for counts: Arrays.stream(nums).boxed().collect(Collectors.groupingBy(x -> x, Collectors.counting())), which is Week 8's topic.

Spring Boot · Week 4Medium

Junk orders are being saved

  • Posting the JSON below returns 201 Created, and the order is saved to MongoDB. Explain why.
  • Fix it so it returns 400, and every order line is checked too.
  • Return the errors as application/problem+json with an errors map of field → message.
Buggy code
public record OrderLine(@NotBlank String sku, @Min(1) int quantity) {}

public record CreateOrderRequest(
    @NotBlank String customerId,
    @Email String email,
    @NotEmpty List<OrderLine> lines) {}

@RestController
@RequestMapping("/api/orders")
class OrderController {
  private final OrderRepository orders; // MongoRepository<Order, String>
  OrderController(OrderRepository orders) { this.orders = orders; }

  @PostMapping
  ResponseEntity<Order> create(@RequestBody CreateOrderRequest req) {
    Order saved = orders.save(Order.from(req));
    return ResponseEntity.created(URI.create("/api/orders/" + saved.id()))
        .body(saved);
  }
}

// POST /api/orders
// {"customerId":"", "email":"nope", "lines":[{"sku":"", "quantity":0}]}
Show solution

Problem 1. No @Valid on the @RequestBody, so the constraints are never checked. Annotations on a record are only metadata until something validates the object. Problem 2. Even with @Valid, List<OrderLine> isn't cascaded, so @NotBlank sku and @Min(1) quantity would still be skipped. Also check that spring-boot-starter-validation is a dependency; without it there's no validator.

Fixed: request, controller, ValidationErrors.java
public record CreateOrderRequest(
    @NotBlank String customerId,
    @Email String email,
    @NotEmpty List<@Valid OrderLine> lines) {}   // cascade into each line

@PostMapping
ResponseEntity<Order> create(@Valid @RequestBody CreateOrderRequest req) {
  Order saved = orders.save(Order.from(req));
  return ResponseEntity.created(URI.create("/api/orders/" + saved.id()))
      .body(saved);
}

@RestControllerAdvice
class ValidationErrors {

  @ExceptionHandler(MethodArgumentNotValidException.class)
  ProblemDetail onInvalidBody(MethodArgumentNotValidException ex) {
    Map<String, String> errors = new LinkedHashMap<>();
    ex.getBindingResult().getFieldErrors().forEach(fe ->
        errors.putIfAbsent(fe.getField(), fe.getDefaultMessage()));

    ProblemDetail pd = ProblemDetail.forStatusAndDetail(
        HttpStatus.BAD_REQUEST, "Request validation failed");
    pd.setTitle("Invalid order");
    pd.setProperty("errors", errors);   // rendered as a top-level field
    return pd;
  }
}

// Response: 400, Content-Type: application/problem+json
// {"type":"about:blank","title":"Invalid order","status":400,
//  "detail":"Request validation failed","instance":"/api/orders",
//  "errors":{"customerId":"must not be blank",
//            "email":"must be a well-formed email address",
//            "lines[0].sku":"must not be blank",
//            "lines[0].quantity":"must be greater than or equal to 1"}}
// (the order of the errors can vary)

How it works. @Valid makes Spring MVC validate the body before calling your method. On failure it throws MethodArgumentNotValidException, so save() never runs. List<@Valid OrderLine> is a container-element constraint that validates each line, and nested errors get paths like lines[0].sku. Returning a ProblemDetail sets the status and the application/problem+json content type. Next week goes deeper into @RestControllerAdvice and ProblemDetail.

Follow-up they'll ask. "Add @GetMapping("/{id}") with @PathVariable @Size(min = 24, max = 24) String id. What's thrown?" A constraint directly on a parameter triggers method validation, which raises HandlerMethodValidationException, not MethodArgumentNotValidException, so handle both. Malformed JSON is a different case: HttpMessageNotReadableException, also a 400.

Best practices · Industry practices

Do this, avoid that

Do

  • Validate at the edge: @Valid on every @RequestBody, with request records separate from your @Document classes.
  • Return one consistent error format (ProblemDetail) for every 4xx, with field paths a front end can map to inputs.
  • Let MongoDB expire short-lived data with TTL indexes, and still check the expiry in code.
  • Create the indexes your queries need explicitly, and review them in code review like schema changes.
  • Give AI agents read-only, narrowly scoped tools first, and add write tools behind a human approval step.

Avoid

  • Adding BindingResult after a @Valid parameter and then never checking it.
  • Returning stack traces or exception class names in 400 responses.
  • A scheduled deleteAll job for expired tokens when a TTL index can do it.
  • Relying on @Indexed with auto-index-creation left off. The index never gets created.
  • Shipping preview APIs like StructuredTaskScope on JDK 27 to production. Wait for the final version in JDK 28.

Real problem, solved with data

"P99 went over 500 ms when writes picked up"

Problem. At idealo, a price-comparison site, event-processing writes and API reads shared one MongoDB cluster. Above about 2,000 events per second, the API's P99 latency rose past 500 ms and broke its SLA.

Diagnosis. The profiler showed MongoDB examining 5 documents for every 1 it returned: about 21 million read a day to return 4 million, because the indexes didn't match the query filters. The slowest requests also hit very large documents, where about 90% of the size was a single offerList field, and one query could transfer up to 8 MB.

Fix. (1) Compound indexes that match the filters brought the ratio to 1:1. Returning 4 M documents now means examining about 4 M, 4 ÷ 21 ≈ 19% of the old work, and about 99% of slow queries disappeared. (2) The team compressed offerList with Zstd in the application. (3) It batched Kafka events into MongoDB bulk writes: 100 events now take 1 round trip instead of 100. Result: P99 stayed below 100 ms, at most 100 ÷ 500 = 20% of the old latency. Throughput went from 2,000 to 9,000 events/s, which is 9,000 ÷ 2,000 = 4.5× (the post rounds this to "4X").

Real numbers from idealo's tech blog post "Advanced MongoDB Performance Tuning" by Sankarganesh Eswaran (2021). The "after" bar for documents examined uses the 1:1 ratio the post reports, applied to 4 M returned. The lesson for a Spring Boot + MongoDB service: check totalDocsExamined vs nReturned with explain() before adding hardware.
