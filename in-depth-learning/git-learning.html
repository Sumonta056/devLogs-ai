01 / 03
Branching properly
How to work on features without stepping on teammates' code
🌿

What is a branch?

A branch is a separate line of work. You make changes there without touching the main codebase until you're ready.

🔀

Why does it matter?

If two devs edit main directly, they overwrite each other. Branches let both work simultaneously, then merge cleanly.

// HOW A FEATURE BRANCH WORKS
branching-workflow.sh
# 1. Always start from an up-to-date main
git checkout main
git pull

# 2. Create your feature branch (name it clearly)
git checkout -b feature/login-page
#   ↑ shorthand for: git branch feature/login-page && git checkout feature/login-page

# 3. Do your work, commit normally
git add .
git commit -m "feat: add login form UI"

# 4. Keep your branch updated with main (do this daily)
git merge main
#   pulls in teammates' changes so you don't fall behind

# 5. When done, go back to main and merge your work
git checkout main
git merge feature/login-page

# 6. Delete the branch (it's merged, you don't need it)
git branch -d feature/login-page
Real tip: Name branches like feature/what-it-does, fix/bug-description, or chore/cleanup-thing. When 10 people are on a team, good branch names are the difference between confusion and clarity.

When two branches edit the same line, Git shows this:

app.txt (conflict)
<<<<<<< HEAD (your branch)
Good morning!
=======
Good evening!
>>>>>>> main

Git is saying: "Both branches changed this line. Which one wins?"

You manually edit the file to keep what you want, then commit:

resolution
# 1. Open the file, delete the conflict markers
#    Keep "Good morning!" OR "Good evening!" OR both
#    Your call — you're the human, Git just flagged the ambiguity

# 2. Stage the resolved file
git add app.txt

# 3. Complete the merge
git commit -m "merge: resolve greeting conflict"

Undoing mistakes
Two tools, very different purposes. Pick the wrong one and you'll confuse your team.
✓ git revert — USE THIS ON SHARED BRANCHES
  • Creates a NEW commit that undoes the bad one
  • History stays intact
  • Safe after pushing
  • Team sees what happened
⚠ git reset — ONLY ON UNPUSHED COMMITS
  • Removes the commit from history
  • Rewrites timeline
  • Dangerous after pushing
  • Can break teammates' repos

BEFORE

a1b2c3d
feat: add login form
e4f5g6h
oops: committed secret key
BAD COMMIT

AFTER: git revert HEAD

a1b2c3d
feat: add login form
e4f5g6h
oops: committed secret key
i7j8k9l
Revert "oops: committed secret key"
NEW COMMIT ✓
revert.sh
# Undo the very last commit (creates a new "undo" commit)
git revert HEAD

# Undo a specific commit by its hash
git revert e4f5g6h

# Revert without auto-committing (lets you review first)
git revert HEAD --no-commit

Removes the commit but keeps your changes staged. Good for "I committed too early."

reset-soft.sh
# Undo last commit, keep changes STAGED (ready to re-commit)
git reset --soft HEAD~1

# Now your files are staged, commit is gone
# Re-commit with a better message:
git commit -m "feat: add login form with proper validation"

# HEAD~1 = one commit back. HEAD~3 = three commits back.

⚠ Removes the commit AND discards all changes. Files are gone. Only use locally, before pushing.

reset-hard.sh
# Nuclear option — commit gone, changes DELETED
git reset --hard HEAD~1

# Reset to match the remote (discard all local changes)
git reset --hard origin/main

# If you did this by mistake, git reflog might save you:
git reflog           # shows ALL recent HEAD positions
git reset --hard HEAD@{2}  # go back to 2 positions ago

Tracing bugs with git log
Production broke. These commands help you find which commit did it.
📋

git log --oneline

Shows compact commit history. Start here when something breaks — scan for suspicious commits.

🔍

git diff

Shows exactly what changed between two points. The diff between yesterday and today often reveals the bug.

🎯

git bisect

Binary searches your commits to find the exact one that broke things. Saves hours on large repos.

👤

git blame

Shows who wrote each line of a file and in which commit. Not about blame — about context.

tracing-commands.sh
# === READING HISTORY ===

# Compact one-line history (your go-to)
git log --oneline
# Output: a1b2c3d feat: add login form
#         e4f5g6h fix: handle null users

# See history for a specific file
git log --oneline -- src/auth/login.js

# === SEEING WHAT CHANGED ===

# What changed in the last 3 commits?
git diff HEAD~3

# What changed between two specific commits?
git diff a1b2c3d e4f5g6h

# === GIT BISECT (the power tool) ===

git bisect start
git bisect bad HEAD       # current state is broken
git bisect good HEAD~20   # 20 commits ago it worked fine

# Git checks out the middle commit automatically
# Test your app — does the bug exist?
git bisect good   # if no bug here
git bisect bad    # if bug exists here
# Repeat until Git says: "e4f5g6h is the first bad commit"

git bisect reset  # go back to HEAD when done
// HOW GIT BISECT WORKS (BINARY SEARCH)

Git halves the search space each round. 20 commits = 5 checks max. 1000 commits = 10 checks.
