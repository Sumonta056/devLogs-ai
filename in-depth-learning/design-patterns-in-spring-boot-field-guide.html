Eight patterns, one Spring Boot codebase

Each pattern below comes with the problem it solves, a flow diagram, production-style Spring Boot code, a use case scenario and a case study. The examples share one world — a news and commerce platform — so you can see how the patterns sit next to each other in a real service.

Creational pattern

Factory

Hand the “which object do I need?” decision to one place, so callers ask for a capability instead of constructing a concrete class.

The problem it solves

Checkout supports bKash, Nagad and card payments. Without a factory, CheckoutService grows a switch on the payment method and imports every gateway class. Adding Rocket next month means editing checkout code, retesting it and risking a regression in a path that touches money.

A factory owns the mapping from “payment method” to “gateway object”. Checkout only knows the PaymentGateway interface. New gateway? Add one class annotated with @Component — nothing else changes.

How it flows

  1. At startup Spring finds every bean implementing PaymentGateway and injects them as a list into the factory.
  2. The factory indexes them by method() into an immutable map — duplicates fail fast at boot.
  3. A request arrives with method = NAGAD; checkout calls factory.get(NAGAD).
  4. The factory returns NagadGateway; checkout calls pay() on the interface and never sees the concrete type.

Spring Boot implementation

Use case scenario

A customer on an e-commerce site picks Nagad at checkout. The controller builds a PaymentRequest, CheckoutService asks the factory for the Nagad gateway and calls pay(). When the business signs Rocket as a fourth provider, a developer adds RocketGateway plus one enum value. Checkout, its tests and the other three gateways stay untouched.

Case study

BeforeA 140-line switch in checkout. Every new provider meant editing the most sensitive class in the system, and two providers once shared a copy-pasted branch with the wrong merchant key.
ChangeEach provider became an isolated @Component with its own config and tests. The factory map rejected duplicate registrations at startup.
ResultAdding a provider became a one-class pull request. Checkout code froze, and a misconfigured provider now fails the deploy instead of failing a real payment.

Seen in the wild

  • Spring’s own BeanFactory / ApplicationContext — the container is a giant factory you ask for objects by type or name.
  • DriverManager.getConnection(url) in JDBC picks the right driver from the URL prefix.
  • Calendar.getInstance() and NumberFormat.getInstance(locale) in the JDK.

When to reach for it

Use when

  • You choose between several implementations of one interface based on input.
  • The set of implementations grows over time.
  • Construction needs config or validation callers shouldn’t care about.

Avoid when

  • There is only one implementation and no sign of a second.
  • A plain new on a simple value object would do.
Creational pattern

Singleton

Guarantee one instance of a class and give everyone the same shared access point to it.

The problem it solves

Some objects are expensive or must be shared: an HTTP client with a connection pool, a cache, a rate limiter that counts OTP requests. If every service creates its own, you waste memory and sockets — and worse, a rate limiter with three instances lets attackers through three times.

In plain Java you write the singleton yourself. In Spring, every bean is a singleton per ApplicationContext by default, so the container does it for you. The real skill is keeping that shared instance thread-safe.

How it flows

  1. Spring creates OtpRateLimiter once during startup.
  2. Every class that needs it gets the same reference through constructor injection.
  3. Concurrent requests update the shared counters through thread-safe structures.
  4. A scheduled task clears the window each minute — one place, one state.

Spring Boot implementation

Use case scenario

Someone scripts 500 OTP requests to one phone number. Because OtpController, LoginService and PasswordResetService all share the same OtpRateLimiter bean, the fourth request inside a minute gets a 429 no matter which endpoint it hits. With separate instances, each endpoint would have allowed three — nine SMS charges instead of three.

Case study

BeforeA developer marked a cart helper bean with a mutable HashMap field, assuming “one per request”. It was a singleton, so carts leaked between users under load.
ChangeStateless beans by default; shared state moved to ConcurrentHashMap or Redis; request-specific data kept in method parameters.
ResultNo more cross-user data. The team added a code-review rule: any field on a singleton bean that isn’t final and thread-safe needs a comment explaining why.

Seen in the wild

  • Every default-scoped Spring bean — controllers, services, repositories.
  • Runtime.getRuntime() in the JDK.
  • A HikariCP DataSource — one pool per application, shared by all repositories.

When to reach for it

Use when

  • The object is expensive (pools, clients, caches) or must have one source of truth.
  • It is stateless, or its state is thread-safe.

Avoid when

  • You need one instance across a cluster — a JVM singleton is per pod; use Redis or a database.
  • You’d store per-user or per-request data in fields; use request scope or parameters.
  • Hand-rolled static singletons in a Spring app — they hide dependencies and hurt testing.
Behavioral pattern

Strategy

Put each variant of an algorithm behind the same interface, so the caller can pick one at runtime without knowing how it works.

The problem it solves

A news site’s front page ranks articles differently per reader: logged-in readers with reading history get personalised ranking, anonymous visitors get trending stories, and if everything else fails the page shows latest-first. Mixing all three algorithms in one method makes it untestable and impossible to A/B test.

Strategy splits each ranking algorithm into its own class. FrontPageService only decides which strategy applies; the strategies decide how to rank.

Factory vs Strategy: they look alike in Spring because both use an interface plus a map of beans. Factory is about getting the right object; Strategy is about swapping behaviour. In practice a factory often hands you a strategy.

How it flows

  1. A reader requests the front page.
  2. FrontPageService inspects the reader context and any experiment flag.
  3. It picks a RankingStrategy by key from an injected map.
  4. The strategy ranks the candidate articles; the service returns the top results.

Spring Boot implementation

Use case scenario

The product team wants to test whether trending ranking beats personalised ranking for subscribers. They set experimentVariant = "trending" for 10% of logged-in readers. No ranking code changes — the service just picks a different strategy, and each strategy has its own unit tests with fixed article lists.

Case study

BeforeOne rankArticles() method with nested ifs for login state, section and experiments. Every tweak to personalisation broke trending in some edge case.
ChangeThree strategy classes, each pure and unit-tested. Selection logic shrank to a few lines in the service.
ResultExperiments became configuration rather than code changes, and a new “editor’s picks” strategy shipped as one new class.

Seen in the wild

  • Comparator passed to List.sort() — the classic JDK strategy.
  • Spring Security’s PasswordEncoder, with DelegatingPasswordEncoder choosing bcrypt, argon2 and others by prefix.
  • Spring’s AuthenticationProvider list and ResourceLoader strategies.

When to reach for it

Use when

  • Several algorithms solve the same problem and the choice depends on context.
  • You want to A/B test or toggle behaviour via config.

Avoid when

  • There are two branches that will never change — an if is clearer.
  • The “strategies” need very different inputs; forcing one interface hides real differences.
Behavioral pattern

Observer

When something happens, announce it once; any number of listeners react on their own, and the announcer doesn’t know who they are.

The problem it solves

When an editor publishes an article, the platform must update the search index, send push notifications, purge the CDN cache and log analytics. If PublishingService calls all four directly, it depends on four teams’ code, and a slow push provider delays the editor’s click.

With Observer, publishing raises an ArticlePublishedEvent. Each concern subscribes on its own. Spring’s ApplicationEventPublisher and @EventListener give you this inside one service; Kafka or RabbitMQ give you the same idea across services.

How it flows

  1. The editor clicks publish; the service updates the article inside a transaction.
  2. It publishes an ArticlePublishedEvent — a small immutable record.
  3. After the transaction commits, Spring delivers the event to every listener.
  4. Slow listeners run @Async so the editor gets an instant response.

Spring Boot implementation

Use case scenario

Breaking news drops. The editor hits publish and gets a response in about 80 ms. Within seconds the article is searchable, the section page is fresh on the CDN, and followers of that section get a push notification. Next quarter the analytics team adds a ReadingTimeEstimateListener without touching PublishingService.

Case study

BeforePublishing called search, push and CDN in sequence. When the push provider had a 20-second outage, editors saw publish spinners hang and clicked again, creating duplicates.
ChangeSide effects moved into AFTER_COMMIT listeners, push made @Async. Later, cross-service events moved to Kafka with an outbox table.
ResultPublish latency stopped depending on third parties, and each listener can fail and retry without affecting the others.

Seen in the wild

  • Spring’s ApplicationEvent system, including ContextRefreshedEvent and ApplicationReadyEvent.
  • DOM addEventListener and Vue’s watch/emit on the frontend.
  • Kafka topics and consumer groups — Observer at distributed scale.

When to reach for it

Use when

  • One action triggers several independent side effects.
  • New reactions get added over time by different people.

Avoid when

  • The caller needs the listener’s result to continue — that’s a direct call.
  • Ordering across listeners matters a lot; implicit flow gets hard to debug.
  • In-memory events must survive a crash — use an outbox plus a broker.
Structural pattern

Adapter

Wrap an incompatible class so it looks like the interface your code already expects — a travel plug for APIs.

The problem it solves

Your app sends OTP and order SMS through a simple SmsSender.send(phone, text) interface. The SMS vendor’s SDK wants a SmsPayload with a different phone format, an encoding flag for Bangla text, and returns status codes as strings. Spreading that SDK through your services ties you to the vendor forever.

An adapter implements SmsSender and translates calls to and from the vendor SDK. Switching vendors means writing a new adapter, not rewriting every caller.

How it flows

  1. OtpService calls smsSender.send("01712345678", text).
  2. The adapter normalises the number to 8801712345678 and detects Bangla text to set Unicode encoding.
  3. It calls the vendor SDK’s submit() with the vendor’s payload type.
  4. It converts the vendor’s response into either success or your own SmsDeliveryException.

Spring Boot implementation

Use case scenario

Marketing negotiates a cheaper SMS vendor. The team writes NewVendorSmsAdapter, runs both adapters side by side behind a feature flag for a week, then deletes the old one. OtpService, OrderNotifier and their tests never change. On a laptop, the local profile swaps in the logging adapter so no real SMS is sent.

Case study

BeforeVendor SDK classes were imported in 11 services. Bangla OTPs arrived as question marks because one caller forgot the Unicode flag.
ChangeOne adapter owned number formatting, encoding and error mapping. The SDK was only imported in that class.
ResultThe encoding bug was fixed in one line for every caller, and the later vendor switch took two days instead of a sprint.

Seen in the wild

  • Spring MVC’s HandlerAdapter lets DispatcherServlet call any kind of handler the same way.
  • SLF4J bindings adapt Logback, Log4j2 and JUL to one logging API.
  • Arrays.asList() and InputStreamReader (bytes to characters) in the JDK.

When to reach for it

Use when

  • Integrating third-party SDKs, legacy systems or external APIs.
  • You want to keep vendor types out of your domain code.

Avoid when

  • You own both sides — just change the interface.
  • The adapter would need to fake behaviour the target can’t really do.
Structural pattern

Decorator

Wrap an object in another object with the same interface to add behaviour — caching, metrics, retries — without changing the original.

The problem it solves

The front page fetches article data from a content API. You need caching, and you need latency metrics. Putting both inside HttpArticleClient mixes networking, caching and observability in one class, and you can’t test or turn them off independently.

Decorators each add one responsibility and delegate the rest. They stack like layers: Timed → Caching → Http. Spring’s @Cacheable and @Transactional are decorators generated as proxies.

Adapter vs Decorator: an adapter changes the interface; a decorator keeps it and adds behaviour.

How it flows

  1. FrontPageService depends on ArticleClient and has no idea it’s wrapped.
  2. The timing decorator starts a Micrometer timer and delegates.
  3. The caching decorator returns a cached article or delegates to the HTTP client.
  4. The result travels back out through the layers; latency is recorded.

Spring Boot implementation

Use case scenario

Traffic spikes on election night. The caching layer serves the same hot articles from memory, so the content API sees a fraction of the calls. Grafana shows article.client.fetch p99 drop from hundreds of milliseconds to near zero. When debugging stale data, an engineer flips one config flag to assemble the stack without the caching layer — the HTTP client and service code are unchanged.

Case study

BeforeCaching, retry and logging lived inside the HTTP client with boolean flags. Tests needed WireMock just to verify the cache.
ChangeEach concern became a small decorator with its own unit test using a fake delegate.
ResultLayers can be reordered (metrics outside cache measures what callers feel; inside measures the API) and added per environment.

Seen in the wild

  • Java I/O: new BufferedReader(new InputStreamReader(inputStream)).
  • Spring AOP proxies behind @Transactional, @Cacheable, @Async and @Retryable.
  • Collections.unmodifiableList() and synchronizedMap().

When to reach for it

Use when

  • You want to add cross-cutting behaviour without touching the core class.
  • Behaviours need to be combined in different ways per environment.

Avoid when

  • The interface is huge — every decorator must delegate every method.
  • An annotation like @Cacheable already does it cleanly.
  • Deep stacks make stack traces hard to read; keep it to a few layers.
Architectural pattern

CQRS

Command Query Responsibility Segregation: use one model to change data and a different, read-optimised model to query it.

The problem it solves

An order system writes with strict rules — stock checks, totals, state transitions — and wants a normalised relational schema. But the “My orders” page and the admin dashboard want fast, denormalised, searchable data with joins across five tables. One model forces a compromise: slow reads or a messy write model.

CQRS splits the two. Commands (PlaceOrder, CancelOrder) go through a domain model into PostgreSQL. Each change emits an event, and a projector builds a flat read model in MongoDB or OpenSearch. Queries only touch the read model. The cost: reads become eventually consistent.

How it flows

  1. The client sends a PlaceOrderCommand; the command service validates business rules and saves to PostgreSQL.
  2. After commit, an OrderPlaced event is published.
  3. The projector writes a flat OrderSummary document to MongoDB.
  4. “My orders” queries hit only the read model — fast, indexed, no joins.

Spring Boot implementation

Production note: an in-memory event is lost if the pod dies between commit and projection. For real systems, write the event to an outbox table in the same transaction and relay it to Kafka (Debezium or a scheduled poller); projectors consume from Kafka. Return 202 Accepted and let the UI show the new order optimistically.

Use case scenario

During an 11.11 sale, order writes jump tenfold, and customers refresh “My orders” constantly. The write side scales on PostgreSQL with short transactions; the read side scales independently on MongoDB replicas. A customer may see their new order a moment after placing it — acceptable — while dashboards never lock order tables.

Case study

BeforeThe admin dashboard ran a six-table join on the live orders database. During sales it caused lock waits and slowed checkout itself.
ChangeDashboard and order history moved to projections in a search/document store, fed by events from the write side.
ResultCheckout latency stopped tracking dashboard usage. New read views became new projectors that replay history — no schema change on the write side.

Seen in the wild

  • The term was coined by Greg Young, building on Bertrand Meyer’s command–query separation; Martin Fowler’s write-up popularised it.
  • Axon Framework for Java is built around CQRS and event sourcing.
  • Search-heavy products commonly keep a relational source of truth and an OpenSearch/Elasticsearch read index — CQRS in practice.

When to reach for it

Use when

  • Reads and writes have very different shapes or load.
  • You need several read views (search, dashboard, history) of the same data.
  • Complex business rules live on the write side.

Avoid when

  • It’s simple CRUD — CQRS doubles the moving parts.
  • Users must always read their own write instantly and you can’t design around it.
  • The team has no way to monitor and rebuild projections.
Architectural / resilience pattern

Circuit Breaker

Watch calls to a dependency; when it keeps failing, stop calling it for a while and return a fallback, then carefully test whether it has recovered.

The problem it solves

The front page calls a recommendation service. When it slows to 10-second responses, every front-page request waits, Tomcat threads pile up, and soon the whole site is down — because one non-critical widget is sick. That is a cascading failure.

A circuit breaker counts failures and slow calls. Past a threshold it opens: calls fail immediately and go to a fallback (latest articles). After a wait it goes half-open, lets a few trial calls through, and closes again if they succeed.

How it flows

  1. Closed: calls go through; Resilience4j records outcomes in a sliding window.
  2. Half of the last 20 calls fail or exceed 2 s — the breaker trips to Open.
  3. Open: calls return the fallback instantly, no network, no waiting threads.
  4. After 30 s, Half-open: three trial calls decide whether to close or reopen.

Spring Boot implementation

Use case scenario

The recommendation service’s database fails over and responses take 8 seconds. Within the first ten or so requests the breaker opens. For the next 30 seconds every reader instantly gets the “Latest news” block instead of “Recommended for you”. The front page stays fast, the struggling service gets breathing room to recover, and /actuator/health shows the breaker state so on-call can see what happened.

Case study

BeforeA slow optional widget exhausted the Tomcat thread pool. The entire site returned 503s although articles and the database were healthy.
ChangeTimeouts on every outbound client, a Resilience4j breaker per dependency, and a meaningful fallback for each.
ResultThe next recommendation outage degraded one widget instead of the whole site. Alerts now fire on breaker state, not on angry readers.

Seen in the wild

  • Popularised by Michael Nygard’s book Release It!.
  • Netflix built Hystrix for this; it is now in maintenance mode and Resilience4j is the usual choice for Spring Boot 3.
  • Service meshes like Istio and gateways like Kong offer outlier detection and passive health checks — the same idea at the network layer.

When to reach for it

Use when

  • Calling remote services that can be slow or down.
  • You have a sensible fallback or can fail fast without harm.
  • One dependency’s failure could exhaust shared resources.

Avoid when

  • Calls are local, in-process and cheap.
  • No timeouts are configured — fix that first, the breaker depends on it.
  • Writes that must not be skipped silently; there, prefer queues and retries.
