01 / 03
Indexes — the table of contents
Without an index, the database reads every single row. With one, it jumps straight to the answer.

📖 The book analogy

A database without indexes is like a book without a table of contents. To find "Chapter 7," you read every page from page 1. An index is the table of contents — you go straight to page 142.

⚡ What it looks like in EXPLAIN

Seq Scan = sequential scan = reads all rows. Slow on big tables.
Index Scan = uses the index. Jumps directly. Fast.

// INTERACTIVE: SEE A FULL TABLE SCAN VS INDEX SCAN

index-demo.sql
-- STEP 1: See a slow query (full table scan)
EXPLAIN ANALYZE
SELECT * FROM users WHERE email = 'user500@example.com';
-- Output includes: Seq Scan on users (cost=...) rows=10000
--                  Execution Time: 8.231 ms

-- STEP 2: Add an index
CREATE INDEX idx_users_email ON users(email);

-- STEP 3: Same query — now uses the index
EXPLAIN ANALYZE
SELECT * FROM users WHERE email = 'user500@example.com';
-- Output includes: Index Scan using idx_users_email
--                  Execution Time: 0.081 ms  ← ~100x faster

When to add an index: If you search, filter, or join on a column frequently, it likely needs an index. The most common ones: user email for login, foreign keys like user_id on posts, and any column you put in a WHERE clause regularly.
02 / 03
The N+1 problem
The most common junior mistake. Running 1 query to get a list, then 1 query per item to get related data.

🐌 N+1 pattern

Get 10 posts (1 query). Loop through them, fetching each post's author (10 more queries). Total: 11 queries for what should be 1.

🚀 JOIN pattern

Get 10 posts WITH their authors in one JOIN query. Total: 1 query. Same result. Database handles the relationship, not your loop.

Watch the queries pile up — one per post:

Press simulate to see what happens

One query. All data. Done.

n-plus-one.sql
-- ❌ THE BAD WAY (N+1)
-- Query 1: get posts
SELECT id, user_id, title FROM posts LIMIT 10;

-- Then your application code loops and runs THIS for each post:
SELECT name FROM users WHERE id = 3;   -- query 2
SELECT name FROM users WHERE id = 7;   -- query 3
SELECT name FROM users WHERE id = 12;  -- query 4
-- ... 10 posts = 11 queries total


-- ✅ THE GOOD WAY (JOIN)
SELECT
  p.id,
  p.title,
  u.name AS author_name
FROM posts p
JOIN users u ON p.user_id = u.id
LIMIT 10;
-- 1 query. Same data. The database does the joining.

-- Run EXPLAIN ANALYZE on both to see the difference yourself:
EXPLAIN ANALYZE SELECT p.id, p.title, u.name
FROM posts p JOIN users u ON p.user_id = u.id LIMIT 10;
How to spot N+1 in your own code: If you see a loop that runs a database query inside it, that's likely N+1. The fix is almost always a JOIN or a bulk fetch (get all the IDs, then WHERE id IN (...)).
03 / 03
The cost of SELECT *
It feels convenient. At scale, it's transferring data your app never even looks at.

Your app only needs id and title to show a post list. But SELECT * fetches everything:

id title user_id body created_at updated_at deleted_at view_count metadata thumbnail_url

data transferred per row, 50,000 posts × 500 concurrent users:

SELECT *
~2,400 bytes
SELECT id, title
~48 bytes
select-comparison.sql
-- ❌ Fetches EVERYTHING — most of it unused
SELECT * FROM posts WHERE user_id = 42;

-- ✅ Only fetch what you actually use
SELECT id, title FROM posts WHERE user_id = 42;

-- Run EXPLAIN ANALYZE on both — notice the width difference:
EXPLAIN ANALYZE SELECT * FROM posts WHERE user_id = 42;
-- width=452 (bytes per row transferred)

EXPLAIN ANALYZE SELECT id, title FROM posts WHERE user_id = 42;
-- width=36 (bytes per row transferred)  ← much less network load
BONUS
The function trap
Wrapping a column in a function silently disables its index. This catches everyone at least once.
function-trap.sql
-- You have an index on email. This query IGNORES it:
SELECT * FROM users WHERE LOWER(email) = 'user@example.com';
-- → Seq Scan. Reads all rows. Index is useless here.
-- Why? The index stores "User@Example.com" — not its lowercased version.

-- Better approach: store emails lowercase AT INSERT TIME
INSERT INTO users (email) VALUES (LOWER('User@Example.com'));
-- Now your indexed query works normally:
SELECT * FROM users WHERE email = 'user@example.com';
-- → Index Scan. Fast.

-- Alternative: create a functional index (more advanced)
CREATE INDEX idx_users_email_lower ON users(LOWER(email));
-- Now LOWER(email) in WHERE will use this index
General rule: If you transform a column in a WHERE clause (LOWER(), DATE(), CAST(), etc.), the index on that column stops working. Transform at insert time instead, or create a functional index.
