REVIEW.md sits next to a short CLAUDE.md

CLAUDE.md tells the reviewer what the project is: stack, conventions, goals. REVIEW.md, written by code owners, tells it what to worry about in their part of the code. Keep it to about a page. Click any part below to see it in the template.

REVIEW.md — example for a Nuxt + Spring Boot service
# REVIEW.md

Read CLAUDE.md first for stack and conventions. This file says what matters in review.

## What failure looks like here
- API (Spring Boot): it returns the wrong data or leaks data. Wrong article,
  wrong user, paywalled content served to a non-subscriber.
- Frontend (Nuxt): it renders differently on server vs client, or breaks
  for logged-out users.
- Config / Kong routes / Helm: it misroutes. Traffic goes to the wrong
  service, or an auth plugin gets dropped.
- DB migrations / Mongo queries: it locks or scans. A missing index, an
  unbounded query, a migration that isn't backward compatible.
- Docs: it lies. The docs describe behaviour the code doesn't have.

## Look hard at
- Auth and subscription checks on every new or changed endpoint
- Personalization: wrong user's reading history, no fallback without history
- Null and empty handling on external responses (OpenSearch, upstream APIs)
- Caching: cache keys that ignore user or subscription state
- Public API contract changes without versioning
- Migrations that can't run while the old version is still deployed

## Don't comment on
- Formatting and import order (ESLint and Spotless enforce these)
- Naming preferences, unless the name is actively misleading
- Max 2 nits per PR. If there are more, say "plus N similar nits" once.

## Skip these paths
- **/generated/**, **/*.lock, package-lock.json, pnpm-lock.yaml
- **/__snapshots__/**, dist/, .nuxt/, build/
- helm/**/values-*.yaml, unless a route, auth plugin or resource limit changes

## Evidence rules
- Every finding cites path/to/file:line and quotes the line.
- Show the input or path that triggers the bug. "This could be null" isn't
  enough; say where the null comes from.
- Don't infer behaviour from a function or variable name. Read the code.
- If the bug existed before this PR, tag it Pre-existing, not Important.

## Output format
Start with one line: N important, N nits, N pre-existing
If nothing needs fixing, say exactly: No issues found.
Then list findings by severity: Important, Nit, Pre-existing.
For a group of the same bug, flag it once and list every location.
Start from real incidentsAnything your team reverted recently becomes the first “look hard at” line.
Move repeat comments inThe same comment twice, from a person or the bot, goes here or into a lint rule.
Keep the two files apartConventions and stack live in CLAUDE.md. Worries for the reviewer live in REVIEW.md.
Check it’s followedEvery few weeks, see if the nit cap and file:line rule hold. If not, the file is probably too long.
