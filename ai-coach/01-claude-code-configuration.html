07
CLAUDE.md: the always-on layer
  • Loaded at the start of every session. It is guidance Claude reads, not a rule the client enforces.
  • Add a line when Claude makes the same mistake twice, or when you retype a correction.
  • Be concrete: “Use 2-space indentation” beats “format code properly”.
  • Target under 200 lines. Longer files cost context and lower adherence.
  • /init drafts one from your codebase, /memory opens it, @path imports another file.
Load order, broadest first
1  managed policy CLAUDE.md 2  ~/.claude/CLAUDE.md 3  ./CLAUDE.md or ./.claude/CLAUDE.md 4  ./CLAUDE.local.md
All of them load together, closest last. A repo with no CLAUDE.md has its AGENTS.md read instead.

When CLAUDE.md gets too big
.claude/rules/
One markdown file per topic, discovered recursively. A rule with no paths frontmatter loads every session. A rule with paths loads only when Claude reads a matching file.
--- paths:   - "src/api/**/*.ts" --- # API rules
Auto memory
Notes Claude writes for itself, on by default, stored per repository under ~/.claude/projects/<project>/memory/.
MEMORY.md is the index and loads each session, capped at 200 lines or 25 KB. Topic files are read on demand.
It records your preferences, your corrections and project decisions — never things it can derive from the code. Toggle it with /memory.

Skills: the on-demand layer
Write one when
  • You paste the same checklist into chat for the third time.
  • A CLAUDE.md section has turned into a procedure rather than a fact.
  • You keep typing the same prompt to start a task.
  • You have reference material Claude needs sometimes, not always.
The body loads only when the skill is used, so long reference costs almost nothing until you need it.
Where it lives decides who gets it
~/.claude/skills/  all your projects .claude/skills/    this repo, commit it <subdir>/.claude/  that folder and below plugin skills/    as /plugin:name managed          the whole organisation
On a name clash: managed wins, then personal, then project.

14
Four things skills can do
Take arguments
$ARGUMENTS for the lot, $0 and $1 by position, or names you declare in frontmatter. /fix-issue 123 just works.
Inject live context
A line like !`gh pr diff` runs before Claude sees the skill, and its output replaces the line in the prompt.
Bundle files and scripts
Keep SKILL.md under 500 lines and move detail into sibling files. ${CLAUDE_SKILL_DIR} resolves the path.
Run in isolation
context: fork hands the skill to a subagent with its own window. It sees no conversation history, so write it to stand alone.
Once invoked, the body stays in context for the rest of the session — every line is a recurring cost.

A skill with the controls turned on
--- name: deploy description: Deploy the application to production context: fork disable-model-invocation: true allowed-tools: Read Grep --- Deploy the application: 1. Run the test suite 2. Build the application 3. Push to the deployment target ## Pull request context - PR diff: !`gh pr diff` - PR comments: !`gh pr view --comments` - Changed files: !`gh pr diff --name-only`
context: fork
Runs in a subagent with a fresh window. It sees none of your history, so the body must stand alone.
disable-model-invocation
Only you can run /deploy. Claude will suggest it rather than decide your code looks ready to ship.
allowed-tools
Pre-approves those tools for the invoking turn only. The grant clears on your next message.
Also available: model, effort, agent, arguments, argument-hint, paths, hooks, disallowed-tools.

19
Permission rules: how they read
Every rule is Tool or Tool(specifier), in one of three lists: allow runs without a prompt, ask always prompts, deny blocks.
  • Order is deny, then ask, then allow. The first match wins and specificity never changes it.
  • An allow rule cannot carve an exception out of a deny rule, at any scope.
  • A bare Bash deny removes the tool from Claude’s context. Bash(rm *) keeps the tool and blocks matching calls.
  • Put the wildcard after the subcommand: Bash(git log *) allows only git log, Bash(git *) allows every git command.
Rule
Matches
Bash
every Bash command
Bash(npm run *)
npm run and anything after
Read(./.env)
reading that one file
Edit(src/**)
edits under src/
WebFetch(domain:*.acme.com)
any acme subdomain
mcp__github__get_*
that server’s get_ tools
Agent(Explore)
the Explore subagent
Run /permissions to see every rule and the settings file it came from.
20
A starter rule set
{   "permissions": {     "defaultMode": "acceptEdits",     "allow": [       "Bash(npm run *)",       "Bash(git status *)",       "Bash(git commit *)",       "WebFetch(domain:docs.internal.com)"     ],     "ask": ["Bash(git push *)"],     "deny": [       "Bash(rm -rf *)",       "Read(./.env)",       "Read(./secrets/**)",       "Edit(./.github/workflows/**)"     ],     "disableBypassPermissionsMode": "disable"   } }
acceptEdits, not bypass
File edits inside the working directory stop prompting. Shell commands still go through the rules.
Ask beats allow
git push prompts every time even though git commit is allowed, because ask is checked first.
Fence off the secrets
A Read deny also blocks Edit and Write on the same path, and covers cat, head and tail in Bash.
Close the escape hatch
disableBypassPermissionsMode stops anyone starting a session that skips prompts entirely.
21
Where a rule stops being a boundary
A Bash rule matches the command text Claude writes, not the program behind it.
Deny rule
Stops
Does not stop
Bash(curl *)
curl https://x
/usr/bin/curl, sh -c 'curl…'
Bash(rm *)
rm -rf build/
/bin/rm -rf build/
Bash(git push *)
git push origin main
git -C . push origin main
Compound commands split
Bash(safe-cmd *) does not approve safe-cmd && other-cmd. Deny and ask still match any subcommand, even inside $( ).
Path anchors differ
/src/** anchors at the settings file’s own root, src/** is relative to the current directory, //path is absolute.
For a real boundary
Turn on sandboxing for OS-level file and network limits, or inspect the full command in a PreToolUse hook.
Deny wins across scopes: a user-level deny blocks a project-level allow, and managed settings beat everything.

Hooks: the guarantee layer
How one runs
  • Claude Code fires an event and your handler reads the event JSON on stdin.
  • Exit 0 is no objection. Exit 2 blocks, and stderr goes back to Claude as feedback.
  • Print JSON on stdout for structured decisions: allow, deny, ask, or extra context.
  • Five types: command, http, mcp_tool, prompt (one model call) and agent (a subagent).
Events you will actually use
SessionStart  SessionEnd UserPromptSubmit PreToolUse  PostToolUse PermissionRequest Stop  SubagentStart  SubagentStop PreCompact  PostCompact FileChanged  ConfigChange
A matcher narrows the event: Edit|Write for file tools, Bash for shell, mcp__github__.* for one server.
A PreToolUse deny holds in every permission mode — even under --dangerously-skip-permissions.
23
Two hooks in one settings file
{   "hooks": {     "PostToolUse": [{       "matcher": "Edit|Write",       "hooks": [{ "type": "command", "command":         "jq -r '.tool_input.file_path'          | xargs npx prettier --write" }]     }],     "Notification": [{       "matcher": "",       "hooks": [{ "type": "command", "command":         "osascript -e 'display notification           \"Claude Code needs your attention\"'" }]     }]   } }
One hooks object
Every event name is a key inside the single hooks object. Add a new event as a sibling rather than replacing what is already there.
Format after every edit
PostToolUse with an Edit|Write matcher. jq pulls the path off the event JSON on stdin and hands it to Prettier.
Know when it needs you
An empty matcher fires on every notification type. osascript on macOS, notify-send on Linux, PowerShell on Windows.
On success a hook shows nothing in the conversation. Check the effect, or run claude --debug to watch it fire.
24
Block edits to protected files
.claude/hooks/protect-files.sh
#!/bin/bash INPUT=$(cat) FILE_PATH=$(echo "$INPUT" | jq -r \   '.tool_input.file_path // empty') # normalize Windows separators FILE_PATH="${FILE_PATH//\\//}" PROTECTED=(".env" "package-lock.json" ".git/") for p in "${PROTECTED[@]}"; do   if [[ "$FILE_PATH" == *"$p"* ]]; then     echo "Blocked: $FILE_PATH hits '$p'" >&2     exit 2   fi done exit 0
Register it in .claude/settings.json
{   "hooks": {     "PreToolUse": [{       "matcher": "Edit|Write",       "hooks": [{         "type": "command",         "command": "\"$CLAUDE_PROJECT_DIR\"           /.claude/hooks/protect-files.sh"       }]     }]   } }
Exit 2 blocks the edit and sends stderr back to Claude as the reason, so it adjusts instead of retrying. Run chmod +x on the script, or the hook errors rather than blocking.
This fires in every permission mode, including bypassPermissions. It is the only way to make “never touch .env” actually hold.
25
Four more worth stealing
Audit configuration changes
ConfigChange fires when a settings or skills file is edited mid-session. Append one JSON line per change for compliance, or exit 2 to block it outright.
Reload the environment
SessionStart and CwdChanged both write direnv output to $CLAUDE_ENV_FILE, so the Bash tool picks up per-directory variables the way your shell does.
Auto-approve one prompt
A PermissionRequest hook matched to ExitPlanMode returns an allow decision as JSON, so a finished plan stops interrupting you. Keep the matcher narrow.
Log and guard together
Two PreToolUse hooks on Bash: one appends every command to a log and exits 0, the other exits 2 on rm -rf. Both run in parallel and the deny wins.

26
MCP: connecting outside systems
  • An open protocol. A server exposes tools, resources and prompts to Claude.
  • Connect one when you keep copying data out of another tab.
  • Tool search is on by default, so idle servers cost almost no context.
  • /mcp shows status, tool counts and runs the OAuth sign-in.
claude mcp add --transport http \   notion https://mcp.notion.com/mcp
Three scopes
local — the default. Stored in ~/.claude.json for this project only, private to you.
project — .mcp.json at the repo root. Committed, and approved once per person.
user — ~/.claude.json, available in all your projects, still private.
Precedence runs local, project, user, plugin, then claude.ai connectors.
Use ${VAR} expansion in .mcp.json so tokens stay out of version control.

Three ways to add a server
1. From a plugin, easiest
Run /plugin, search jira, install atlassian from claude-plugins-official. The server, its skills and its agents arrive together.
2. From a URL
claude mcp add --transport http \   atlassian https://mcp.atlassian.com/v1/mcp
3. From someone else’s JSON
Setup written for another MCP client uses the same entry shape. Pass the object inside mcpServers to claude mcp add-json.
{   "mcpServers": {     "example": {       "command": "npx",       "args": ["-y", "@example/mcp-server"]     }   } }
Demo
Install atlassian, then ask Claude to create a Jira issue from the bug we just fixed. Watch the permission prompt name the exact tool before anything is written.
An entry with a url but no type is read as a stdio server and skipped. Add "type": "http".
29
Let it read, not delete
Gate the tools with permission rules
"permissions": {   "allow": [     "mcp__atlassian__jira_search",     "mcp__atlassian__get_*"   ],   "ask":  ["mcp__atlassian__create_*"],   "deny": ["mcp__*__delete_*"] }
An allow glob needs a literal server prefix. Deny and ask accept a glob anywhere, so mcp__* blocks every MCP tool at once.
Pin the OAuth scopes you were granted
"slack": {   "type": "http",   "url": "https://mcp.slack.com/mcp",   "oauth": {     "scopes": "channels:read chat:write search:read"   } }
This is the supported way to hold a server to a security-approved subset when it advertises more than you want to grant.
Also: toggle a server off per project in /mcp, reject one by name with disabledMcpjsonServers, and connect databases with a read-only user.

Subagents: work in a separate context
  • Its own context window, system prompt, tool set and model.
  • Only the summary comes back, so the main conversation stays clean.
  • Built in: Explore for read-only search, Plan for plan mode, general-purpose for the rest.
  • A fork, started with /subtask, is a subagent that inherits the whole conversation.
Files live in .claude/agents/ or ~/.claude/agents/. Other fields: disallowedTools, permissionMode, skills, memory, maxTurns, isolation.
--- name: code-reviewer description: Reviews code for quality and   security. Use after writing code. tools: Read, Grep, Glob model: sonnet --- You are a senior code reviewer. Report findings by priority, and give a concrete fix for each one.
Keep descriptions short: they sit in context all session, and the combined budget is 15,000 tokens.
