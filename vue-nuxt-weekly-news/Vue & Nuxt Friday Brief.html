Must-have this week

If you only take three things

  1. Before you bump @vueuse/core to 15, read the breaking changes. useThrottleFn now defaults to trailing: true, templateRef is gone (use Vue's useTemplateRef), and Node 20 support was dropped.
  2. When SSR calls Spring Boot, forward only the cookie header with useRequestHeaders(['cookie']). Don't forward everything (Snippet 2).
  3. Check your routeRules. Any route with swr, isr or prerender serves the same HTML to every visitor, so it must never render per-user data. The Nuxt interview question below explains why.

Nuxt 4.5Stable

Named views: one route, several <NuxtPage> outlets

From the docs: "A single route can render into multiple <NuxtPage> outlets in a parent component by giving each outlet a name and providing a sibling page file for each name." It's Vue Router's named views, set up through file names instead of a hand-written routes array.

1 · Name the fileNext to child.vue, add child@sidebar.vue
2 · Add an outletThe parent renders <NuxtPage /> and <NuxtPage name="sidebar" />
3 · NavigateOn /parent/child, each file renders into its matching outlet. Outlets with no matching file stay empty

Turn it on

app/pages/orders.vue · orders/[id].vue · orders/[id]@sidebar.vue
# file layout (Nuxt 4.5+, no config flag needed)
app/pages/
  orders.vue
  orders/
    [id].vue            # → default outlet
    [id]@sidebar.vue    # → outlet named "sidebar"

<!-- app/pages/orders.vue -->
<template>
  <div class="grid">
    <NuxtPage />
    <aside><NuxtPage name="sidebar" /></aside>
  </div>
</template>

<!-- orders/[id]@sidebar.vue: params work as usual -->
<script setup lang="ts">
const route = useRoute()
const { data: history } = await useFetch(() => `/orders/${route.params.id}/history`, {
  baseURL: useRuntimeConfig().public.apiBase,
})
</script>

Watch out for

  • definePageMeta is only read from the default route file. Meta written in a name@view.vue file "has no effect on the route", so middleware and layout belong in [id].vue.
  • The 4.5 release notes say "per-view rendering modes aren't supported". The whole route shares one rendering mode, so you can't, for example, make only the sidebar client-only through route rules.
  • Outlets with no matching named file render nothing, so plan an empty state for the <aside>.
  • Requires Nuxt 4.5 or later.

In your project: it suits master-detail screens backed by Spring Boot. The default view shows the order (GET /orders/{id}) and the sidebar view shows its audit trail (GET /orders/{id}/history, perhaps a Mongo sub-collection). Each view fetches its own data and owns its loading state, and the parent page doesn't need v-if logic to decide what goes in the aside.

Official docs: Pages → Named Views (v4.5)
Vue 3.5+Stable

useId(): SSR-safe IDs for labels and ARIA

The docs say it is "used to generate unique-per-application IDs for accessibility attributes or form elements". The IDs are "guaranteed to be stable across the server and client renders", so you can stop using Math.random() ids and counters, which cause hydration mismatches.

1 · CallCall useId() in setup. Each call, and each component instance, gets a new id
2 · BindUse it for :for/:id, aria-describedby and aria-controls
3 · HydrateThe server and client generate the same string, so there's no mismatch warning

Turn it on

components/FormField.vue
<script setup lang="ts">
import { useId } from 'vue'   // auto-imported in Nuxt

defineProps<{ label: string; error?: string }>()
const model = defineModel<string>()
const id = useId()               // call in setup, NOT inside computed()
const errorId = `${id}-error`
</script>

<template>
  <label :for="id">{{ label }}</label>
  <input :id="id" v-model="model"
         :aria-invalid="!!error"
         :aria-describedby="error ? errorId : undefined" />
  <p v-if="error" :id="errorId">{{ error }}</p>
</template>

// two Vue apps on one page? give each a prefix
app.config.idPrefix = 'admin'    // ids become 'admin:0', 'admin:1', …

Watch out for

  • The docs warn that useId() "should not be called inside a computed()", because it may cause instance conflicts. Create the id once outside and reference it inside.
  • IDs are unique per application. If more than one Vue app mounts on the same page, set app.config.idPrefix for each so the ids don't collide.
  • Don't use them as data keys or persist them. They identify DOM nodes for one render tree and mean nothing to your API.

In your project: pair it with last week's ProblemDetail handling. When Spring returns a 400 with field errors, render each message in a <p :id="errorId"> linked through aria-describedby, so screen readers announce the server's message for that exact field. Nuxt 4 auto-imports Vue's useId; there's no separate Nuxt version in the 4.x docs.

Official docs: Composition API helpers → useId()

Props with defaults, no withDefaults Basic · Vue 3.5+

Reactive props destructure lets you write defaults with plain JavaScript syntax. The catch: pass a getter to watch or to a composable, not the destructured value.

components/OrderBadge.vue
<script setup lang="ts">
type OrderStatus = 'PENDING' | 'PAID' | 'SHIPPED' | 'CANCELLED'  // mirrors the Java enum

const { status = 'PENDING', compact = false } =
  defineProps<{ status?: OrderStatus; compact?: boolean }>()

const label = computed(() => status.charAt(0) + status.slice(1).toLowerCase())

// ❌ watch(status, …) passes a plain value, and Vue's compiler warns
watch(() => status, (now, before) => {     // ✅ getter keeps it reactive
  if (now === 'CANCELLED') console.info(`order went ${before} → ${now}`)
})
</script>

<template>
  <span :class="['badge', status.toLowerCase(), { compact }]">{{ label }}</span>
</template>

Gotcha: to hand a destructured prop to your own composable, write useThing(() => status). Inside it, read the value with toValue().

Forward the session cookie to Spring Boot during SSR Intermediate · Nuxt 3.x/4.x + Spring Security

During SSR the request to Spring comes from the Nuxt server, not the browser, so the user's JSESSIONID doesn't go with it unless you pass it on. Forward that one header only.

app/composables/useMe.ts
export interface Me { id: string; email: string; roles: string[] }

export function useMe() {
  const config = useRuntimeConfig()
  // SSR: { cookie: 'JSESSIONID=…' } · browser: {} (empty object, per the docs)
  const headers = useRequestHeaders(['cookie'])

  return useFetch<Me>('/api/users/me', {
    key: 'me',
    baseURL: config.public.apiBase,      // e.g. https://api.example.com
    headers,                             // only the cookie, never host/content-length/x-forwarded-*
    credentials: 'include',             // browser-side calls send the cookie cross-origin
  })
}

// in a page or middleware
const { data: me, error } = await useMe()

Why it matters: the docs warn: "Be very careful before proxying headers to an external API and just include headers that you need". host, content-length and the x-forwarded-* headers should never be forwarded. If Spring sets a cookie in its SSR response, the same docs page has a fetchWithCookie recipe that copies set-cookie back to the browser with appendResponseHeader.

Cache Spring Data pages and refresh them after a mutation Advanced · @pinia/colada 1.x (+ @pinia/colada-nuxt)

Pinia Colada caches each query under a key. One mutation can then invalidate every page of a list, because keys match hierarchically: ['orders'] also matches ['orders', 'c42', 0].

app/composables/orders.ts
import { useQuery, useMutation, useQueryCache } from '@pinia/colada'
import type { Page } from '~/types/page'   // { content, page: {...} } from last week
import type { Order } from '~/types/order'

export function useOrders(customerId: MaybeRefOrGetter<string>, pageNo: MaybeRefOrGetter<number>) {
  const { $api } = useNuxtApp()             // your $fetch.create() instance
  return useQuery({
    key: () => ['orders', toValue(customerId), toValue(pageNo)],   // reactive key
    query: () => $api<Page<Order>>('/orders', {
      query: { customerId: toValue(customerId), page: toValue(pageNo), size: 20 },
    }),
  })
}

export function useCancelOrder() {
  const { $api } = useNuxtApp()
  const queryCache = useQueryCache()
  return useMutation({
    mutation: (id: string) => $api(`/orders/${id}/cancel`, { method: 'POST' }),
    // success or failure: re-sync every cached orders page
    onSettled: () => queryCache.invalidateQueries({ key: ['orders'] }),
  })
}

// page: const { data, status, refresh } = useOrders(customerId, page)
//       const { mutate: cancel, asyncStatus } = useCancelOrder()

Why it matters: without this, a cancel on page 2 leaves page 1's cached copy stale. Add exact: true when you mean one key only. For optimistic UI, the invalidation guide shows onMutate + setQueryData with a rollback in onError.

Tips & tricks

Small things that save time

Check useThrottleFn calls before VueUse 15The default trailing changed from false to true, so a throttled "save" handler can now fire one extra time at the end of a burst. Pass trailing explicitly if your code depends on the old behaviour.
Make sure CI runs Node 20.19 or newerh3 v2 requires Node 20.19+, and VueUse 15 dropped Node 20 support altogether. Update engines and the CI image before Nitro moves to h3 v2.
Try defineRouteRules inside a pageWith experimental.inlineRouteRules: true, a page can declare defineRouteRules({ prerender: true }) itself. Regex params like /:id(\d+) can't be converted to a rule pattern and are silently skipped.
Use useLayout() to read the active layoutNew in Nuxt 4.5, it returns a read-only computed ref of the resolved layout. That's handy for analytics or for hiding a header on layout === 'auth'.
Smoke-test 3.6.0-rc.10 in a branchrc.10 changes useModel to keep its local value when the prop didn't change. If you wrote defineModel workarounds, run your form tests against the RC now.

Best practices & industry practices

What teams are standardising on

Taken from Nuxt's data-fetching and rendering docs, the Vue props guide, and how Spring Security handles credentialed CORS.

Do

  • Allowlist the headers you forward from SSR to your API. Usually that's just cookie or authorization.
  • Choose a rendering mode per route. prerender for marketing pages, swr/isr for public catalogues, plain SSR for anything personalised, ssr: false for admin areas.
  • Use useId() for every label/input and aria-* pairing in SSR apps.
  • Key client caches hierarchically (['orders', customerId, page]) so you can invalidate a whole family at once.
  • Allow an explicit list of origins with credentials on the Spring side.

Retire

  • Math.random() or module-level counters for DOM ids. They change between server and client.
  • withDefaults() in new code on Vue 3.5+. Destructure with defaults instead.
  • Forwarding useRequestHeaders() with no filter. It leaks host and x-forwarded-* to an external API.
  • VueUse's templateRef. It was removed in v15; use Vue's useTemplateRef.
  • allowedOrigins("*") together with credentials. Spring refuses that combination; list origins or use allowedOriginPatterns.
Spring Boot · CORS for a Nuxt front end that sends cookies
// WebConfig.java: only matters for calls made by the BROWSER.
// SSR calls from the Nuxt server are server-to-server and ignore CORS.
@Configuration
class WebConfig implements WebMvcConfigurer {
  @Override
  public void addCorsMappings(CorsRegistry registry) {
    registry.addMapping("/api/**")
        .allowedOrigins("https://app.example.com", "http://localhost:3000")
        .allowedMethods("GET", "POST", "PUT", "PATCH", "DELETE")
        .allowCredentials(true);   // pairs with credentials: 'include' in Nuxt
  }
}
// With Spring Security, also call http.cors(Customizer.withDefaults())

VueMid → SeniorReactivity · watchers
A search box calls a Spring Boot endpoint, and the page also shows a filtered total. Which do you use for each: computed, watch or watchEffect? And how do you stop a slow, older response from overwriting a newer one?

Asked in: Hyring's Vue set (Q5 "When do you use computed versus watch?", rated for freshers, and Q24 "What is the difference between watch and watchEffect?", rated intermediate), GreatFrontEnd's Vue interview guide ("If you can calculate it during render, use computed"), and SharpSkill's 25 essential Vue questions (watchEffect vs watch). The race-condition follow-up is what moves it up to senior level.

What they're really testing

  • Can you tell derived state (no side effects, cached) apart from side effects that react to a change?
  • Do you know watcher cleanup and dependency tracking well enough to prevent stale-response bugs?
Show model answer

30-second version: the total is derived from state, so it's a computed: cached, declarative, and recalculated only when its dependencies change. The API call is a side effect, so it's a watch on the query. That gives an explicit source, it's lazy by default, and you get the new and old values. watchEffect runs immediately and tracks whatever it reads, but only during its synchronous part, so anything read after the first await isn't tracked. For races, register a cleanup with onWatcherCleanup() (Vue 3.5+) that aborts the previous request before the next run starts. In Nuxt, useFetch with a reactive query does this for you.

SearchOrders.vue
<script setup lang="ts">
import { ref, computed, watch, onWatcherCleanup } from 'vue'

const q = ref('')
const results = ref<Order[]>([])

// ✅ derived state → computed (cached, no side effects)
const total = computed(() => results.value.reduce((s, o) => s + o.amount, 0))

// ✅ side effect → watch with an explicit source
watch(q, async (term) => {
  const controller = new AbortController()
  onWatcherCleanup(() => controller.abort())   // runs before the next call · must be registered before any await
  try {
    results.value = await $fetch<Order[]>('/api/orders/search', {
      query: { q: term }, signal: controller.signal,
    })
  } catch (e) {
    if (!controller.signal.aborted) throw e      // ignore our own aborts
  }
})
</script>

// Nuxt shortcut: reactive query + default dedupe:'cancel' handles the race
// const { data } = await useFetch('/api/orders/search', { query: { q } })
Junior answer"Computed is cached, watch is for when something changes." That's correct, but it stops there and puts the fetch in a watchEffect with no cleanup.
Senior answerUses computed for derived state and watch for effects. Explains that watchEffect only tracks the synchronous part before the first await. Fixes the race with onWatcherCleanup (or the onCleanup third argument on older versions). Points out that Nuxt's useFetch already cancels superseded requests, and mentions debouncing so the Spring API isn't hit on every keystroke.

Likely follow-ups

  1. How do you run the watcher once at start? ({ immediate: true }. And { once: true }, Vue 3.4+, fires only on the first change.)
  2. You need the updated DOM inside the callback. What do you do? (flush: 'post', or watchPostEffect().)
  3. When does a watcher not stop on unmount? (When it was created asynchronously, for example after an await or inside a setTimeout. Call the returned stop function yourself.)

Common mistake: using watch to copy derived values into another ref (watch(items, v => total.value = sum(v))). You end up with two sources of truth, an extra render, and a value that can be out of date for one tick. If you can calculate it during render, use computed.

NuxtSeniorHybrid rendering · routeRules · caching
Your Nuxt app has a public product catalogue, a marketing home page, a logged-in "My orders" page and an internal admin. All of it is backed by Spring Boot. Configure rendering per route, and tell me where each cache lives and what could go wrong.

Asked in: GoodSpace's 2026 Nuxt set (Q14 "What are the rendering modes in Nuxt 3 and when do you use each?", Q16 "What is hybrid rendering and how does ISR work in Nuxt 3?", Q34 on on-demand ISR revalidation), Vue School's "Nuxt Rendering Modes and Hybrid Rendering" article, and Nuxt SEO's "Rendering for SEO in 2026" guide.

What they're really testing

  • Do you know what each route rule does, and which ones only take effect on certain hosting platforms?
  • Do you understand that a cached page is shared across users, and the cross-user data leak that follows if you cache the wrong page?
Show model answer

30-second version: use routeRules, Nuxt's hybrid rendering. The home page is prerender: true, rendered once at build time and served as a static file. The catalogue is swr: cache headers are added and the response is cached "on the server or reverse proxy for a configurable TTL". On Netlify or Vercel, isr pushes it into the CDN cache instead. "My orders" stays plain SSR with no cache, because the HTML contains one user's data. Admin gets ssr: false and renders only in the browser. The main risk: if you put swr, isr or prerender on a personalised page, the first user's orders get served to everyone.

nuxt.config.ts · server/api/categories.get.ts
export default defineNuxtConfig({
  routeRules: {
    '/':            { prerender: true },   // built once at build time; data must exist at build time
    '/products/**': { swr: 600 },        // cached 10 min on Nitro/proxy, revalidated in background
    // on Vercel/Netlify: '/products/**': { isr: 600 } → CDN cache
    '/orders/**':   { headers: { 'cache-control': 'private, no-store' } }, // SSR, never shared
    '/admin/**':    { ssr: false },       // SPA island, no server HTML
    '/old-shop':    { redirect: '/products' },
  },
})

// server/api/categories.get.ts: cache an expensive Spring call in Nitro
export default defineCachedEventHandler(async (event) => {
  return $fetch(`${useRuntimeConfig(event).apiBase}/categories`)  // private runtime config
}, { maxAge: 60 * 10 })

Where each cache lives: prerender produces static files in the build output. swr caches on the Nitro server or a reverse proxy. isr uses the platform CDN, currently Netlify or Vercel per the docs. None of them replace HTTP caching on the Spring side, so public GETs there can still send their own Cache-Control.

Junior answerLists "SSR, SSG, SPA" and puts swr: true on everything "for speed".
Senior answerPicks a mode per route and explains why. Knows isr needs platform support. Treats shared caches as public-only and marks personalised responses private. Thinks about invalidation (TTL vs on-demand). Adds defineCachedEventHandler for hot server routes and mentions page-level defineRouteRules (experimental).

Likely follow-ups

  1. Can a page declare its own rule? (Yes. defineRouteRules() inside the page, behind experimental.inlineRouteRules. Paths with regex params, partial segments or repeatable params are not converted, so their rules aren't applied.)
  2. swr vs isr? (Both cache the response for a TTL. isr can also add it to the CDN cache on platforms that support it, currently Netlify and Vercel.)
  3. How would you keep a few pages script-free? (noScripts: true disables Nuxt scripts and JS resource hints, which works for purely static legal or landing pages.)

Common mistake: thinking a cached SSR page is per-user because "it's server-rendered". A swr/isr response is one HTML document shared by every visitor until it's revalidated. Personalised content must be uncached SSR or fetched on the client after hydration.
