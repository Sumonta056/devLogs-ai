Must-have this week

If you only take three things

  1. Upgrade to Nuxt 4.6.3 (27 Oct) now with npx nuxt upgrade --dedupe. It fixes five advisories. The worst (Moderate, CVSS 6.5) affects 4.6.0–4.6.2: a path like /%2e/admin renders a protected page while skipping path-based server/middleware checks, server redirects and per-route headers such as CSP. server/api routes aren't affected.
  2. Set NUXT_APP_SECRET yourself, even in dev. On 4.6.0–4.6.2, an exposed nuxt dev server let anyone download the generated .nuxt/app-secret and forge useSession cookies. If you ever ran nuxt dev --host on a shared network, delete that file after upgrading. Production builds weren't affected.
  3. Try Nuxt DevTools v4 on a branch: npx nuxt module add @nuxt/devtools@4 (Nuxt 4.5+). It's built on Vite DevTools and now includes the full Vue DevTools. No app changes are needed, but older modules log NDT_DEP_* warnings until they migrate.

Nuxt 4.6Experimental

Typed $fetch from generated routes: routeTypedFetch

From the docs, it types $fetch and useFetch "from the routes your server builder reports", not from Nitro's InternalApi. The generated route set includes the body, query and headers each handler validates, plus its response as it arrives over the wire. It's built on fetchdts, and the upgrade guide says the old approach didn't scale beyond about 300 routes. The new one costs the same at any size.

1 · Opt inSet experimental.routeTypedFetch: true or future.compatibilityVersion: 5
2 · ValidateHandlers that use readValidatedBody / getValidatedQuery become part of a generated route tree
3 · Check callsA missing or wrong body, or a method the route doesn't answer, is a type error. A Date becomes string

Turn it on

nuxt.config.ts · server/api/orders.post.ts · any page
// nuxt.config.ts
export default defineNuxtConfig({
  experimental: { routeTypedFetch: true },
})

// server/api/orders.post.ts: a BFF route in front of Spring
import { defineEventHandler, readValidatedBody, useRuntimeConfig } from 'nuxt/server'
import { z } from 'zod'

export default defineEventHandler(async (event) => {
  const body = await readValidatedBody(event, z.object({ sku: z.string(), qty: z.number().int().positive() }))
  return $fetch<{ id: string; createdAt: string }>('/api/orders', {
    baseURL: useRuntimeConfig().springApiBase, method: 'POST', body,
  })
})

// in a page or composable
await $fetch('/api/orders', { method: 'post', body: { sku: 'A-1', qty: 2 } })     // ok
await $fetch('/api/orders', { method: 'post', body: { sku: 'A-1', qty: '2' } })   // ✗ string not assignable to number
await $fetch('/api/orders', { method: 'post' })                                  // ✗ body is required

Watch out for

  • It's opt-in on Nuxt 4 because it's stricter. The params option (an alias for query) is no longer accepted, so rename it to query first.
  • Routes you added by hand-augmenting InternalApi are no longer picked up. Move them to ServerRoutes from @nuxt/schema using the Endpoint type from nuxt/app.
  • Paths the generated types don't describe resolve as unknown. experimental.strictRouteTypes (which needs routeTypedFetch) turns unknown paths into errors, but then files in public/ need an explicit response type.
  • The flag is temporary. From Nuxt 5 this typing is the only source and the option is removed.

In your project: this only types routes Nuxt's server builder knows about. A useFetch that goes straight to Spring through baseURL gets no route types. You get the full benefit when the browser calls Nuxt BFF routes, like the one above, that validate input with zod before forwarding to Spring. That also gives you one place to keep the Spring contract in sync. Rename any params: to query: before you switch it on.

Official docs: Experimental features → routeTypedFetch · Nuxt 5 upgrade notes
Vue Router 5.4Experimental

Per-page scroll restoration with useScrollRestoration

From the docs, the ScrollRestoration plugin and the useScrollRestoration() composable from vue-router/experimental save and restore scroll positions per page. They replace the deprecated scrollBehavior router option. Positions live in sessionStorage, so they survive a reload in the same tab. You can save several positions at once (window plus a sidebar), and use custom restore logic such as scrollIntoView().

1 · PluginInstall ScrollRestoration before the router, with the default capture and restore
2 · CaptureThe page you leave is captured after each navigation, on pagehide and when the tab is hidden
3 · RestoreuseScrollRestoration() in a layout or page restores via onRouteRendered, after <Suspense> and out-in transitions

Turn it on

main.ts · pages/Orders.vue (Vue SPA)
// main.ts
import { createApp } from 'vue'
import {
  ScrollRestoration,
  SCROLL_RESTORATION_CAPTURE_DEFAULT,
  SCROLL_RESTORATION_RESTORE_DEFAULT,
} from 'vue-router/experimental'
import App from './App.vue'
import { router } from './router'

const app = createApp(App)
app.use(ScrollRestoration, {              // must come before app.use(router)
  router,
  capture: SCROLL_RESTORATION_CAPTURE_DEFAULT,
  restore: SCROLL_RESTORATION_RESTORE_DEFAULT,
})
app.use(router)
app.mount('#app')

// pages/Orders.vue: list loaded from Spring after mount, so restore manually
<script setup lang="ts">
import { nextTick, onMounted, ref } from 'vue'
import { useScrollRestoration } from 'vue-router/experimental'

const orders = ref<{ id: string }[]>([])
const { scroll } = useScrollRestoration({ manual: true })

onMounted(async () => {
  const res = await fetch('/api/orders?page=0&size=50')   // Spring Data page
  orders.value = (await res.json()).content
  await nextTick()
  scroll()                                // restore once the rows are in the DOM
})
</script>

Watch out for

  • It's experimental and "might have breaking changes". The docs don't name a minimum version. It arrived in the 5.4.0 release.
  • The plugin does nothing alone, so at least one component must call useScrollRestoration(). Don't call it in App.vue or outside a <RouterView>, or the restore runs on the old page.
  • Installing it sets history.scrollRestoration to manual, which can conflict with anchor links. capture() and restore() must be synchronous, and each capture writes to sessionStorage synchronously, so throttle frequent captures.
  • Sibling components active at the same time need distinct keys. A nested call with the same key replaces its parent's.

In your project: the docs describe plain Vue Router apps, not Nuxt, which manages scrolling through app/router.options.ts. So try it first in a Vue SPA, such as an internal admin panel on top of Spring. Pair manual: true with Spring-paged lists so you restore only after the page of results has rendered. For virtualized lists, call scroll() once the virtualizer has measured.

An accessible field that shows Spring validation errors Basic · Vue 3.5+

useId() gives SSR-stable ids for for/aria-describedby, and useTemplateRef() lets the parent focus the first invalid field after a 400 from Spring.

app/components/FormField.vue
<script setup lang="ts">
import { useId, useTemplateRef } from 'vue'

const props = defineProps<{ label: string; error?: string }>()
const model = defineModel<string>({ default: '' })

const id = useId()                        // stable across server and client: no hydration mismatch
const errorId = `${id}-error`
const input = useTemplateRef<HTMLInputElement>('input')

defineExpose({ focus: () => input.value?.focus() })
</script>

<template>
  <label :for="id">{{ label }}</label>
  <input
    ref="input" :id="id" v-model="model"
    :aria-invalid="!!error"
    :aria-describedby="error ? errorId : undefined"
  />
  <p v-if="error" :id="errorId" role="alert">{{ error }}</p>
</template>

From the docs: useId() ids are "stable across the server and client renders". Don't call it inside computed(), because that "may cause instance conflicts". useTemplateRef returns a read-only shallow ref, so it's null until mount. Feed error from Spring's field errors (for example a Map<field, message> built from MethodArgumentNotValidException).

One $api for Spring: base URL, auth header and Problem Details Intermediate · Nuxt 3+ / 4.x

Nuxt's recipe for a custom fetcher, adapted to Spring Boot. It handles the 401 redirect in one place and turns RFC 9457 Problem Details (title, status, detail) into readable errors.

app/plugins/api.ts · app/pages/orders.vue
// shared/types/problem.ts (auto-imported in Nuxt 4)
export type ProblemDetail = { title?: string; status?: number; detail?: string; instance?: string }


// app/plugins/api.ts
export default defineNuxtPlugin((nuxtApp) => {
  const { apiBase } = useRuntimeConfig().public
  const token = useCookie<string | null>('access_token')   // or read from your session

  const api = $fetch.create({
    baseURL: apiBase,
    onRequest({ options }) {
      if (token.value) options.headers.set('Authorization', `Bearer ${token.value}`)
    },
    async onResponseError({ response }) {
      if (response.status === 401) {
        await nuxtApp.runWithContext(() => navigateTo('/login'))
      }
      // other errors: the parsed body (Spring's ProblemDetail) ends up on error.data
    },
  })

  return { provide: { api } }
})

// app/pages/orders.vue  (Spring: spring.mvc.problemdetails.enabled=true)
const { $api } = useNuxtApp()
const { data, error } = await useAsyncData('orders', () => $api('/api/orders', { query: { page: 0, size: 20 } }))
const message = computed(() => (error.value?.data as ProblemDetail | undefined)?.detail ?? 'Something went wrong')

Why this shape: the docs say $fetch is "intentionally not globally configurable", so a $fetch.create instance is the supported way to set defaults. Wrap it in useAsyncData, which "avoids double data fetching" during SSR and hydration. navigateTo runs inside nuxtApp.runWithContext because the hook fires outside the component's setup. A token in a readable cookie is only for illustration. Last week's sealed-session BFF is safer.

Reuse already-fetched Spring data on client navigation Advanced · Nuxt 4.x

By default, going back to a page refetches its data. A custom getCachedData returns what's already in the payload, except when the user explicitly refreshes.

app/pages/catalogue.vue
<script setup lang="ts">
interface Category { id: string; name: string }

const { data: categories, refresh } = await useFetch<Category[]>('/api/categories', {
  baseURL: useRuntimeConfig().public.apiBase,
  key: 'categories',
  getCachedData(key, nuxtApp, ctx) {
    if (ctx.cause === 'refresh:manual') return undefined  // user clicked "Refresh": go to Spring
    return nuxtApp.payload.data[key] ?? nuxtApp.static.data[key]
  },
})
</script>

<template>
  <button @click="refresh()">Refresh</button>
  <ul><li v-for="c in categories" :key="c.id">{{ c.name }}</li></ul>
</template>

From the docs: the signature is (key, nuxtApp, ctx) => DataT | undefined, where ctx.cause is 'initial' | 'refresh:manual' | 'refresh:hook' | 'watch'. Returning undefined means "fetch". The default only reads the payload while hydrating. Use this for reference data (categories, currencies), never for per-user or price-sensitive data. That data stays cached for as long as the tab is open.

Tips & tricks

Small things that save time

Upgrade with --dedupenpx nuxt upgrade --dedupe refreshes the lockfile, so you don't end up with an old, vulnerable @nuxt/vite-builder or @nuxt/nitro-server alongside the new nuxt. Nuxt 4.6 needs Node ^22.22.3 || ^24.15.0 || >=26.0.0.
Nested mutations on useFetch data don't re-renderIn Nuxt 4, deep defaults to false "for improved performance (shallow ref object)". Replace data.value instead of pushing into it, or pass deep: true for that one call.
Pass props into composables as gettersWrite useOrder(() => props.id) or toRef(() => props.id), which the docs call "recommended in 3.3+", instead of props.id. A plain value is read once and loses reactivity.
Open DevTools from the keyboardShift + Option + D on macOS, or Shift + Alt + D on Windows. The shortcut is unchanged in v4.
Redirect rules are not a lockThe 4.6.3 advisory spells it out: "Redirect rules are not an access control mechanism." Put real checks in Spring, or in Nuxt server routes, not in routeRules.

Best practices & industry practices

What teams are standardising on

Based on this week's Nuxt security advisories, the custom-fetch recipe, Vue's composables guide and the Nuxt 5 upgrade notes.

Do

  • Authorize every request in Spring Security. Nuxt middleware is for UX: redirects and hiding links.
  • Set NUXT_APP_SECRET explicitly in every environment, including shared dev and staging.
  • Create one $fetch.create instance for the Spring API, with base URL, auth and error mapping in one place.
  • Have composables accept MaybeRefOrGetter, read with toValue() inside a watcher, and return a plain object of refs.
  • Apply security headers through routeRules, and re-test them on odd paths after each upgrade.

Retire

  • Path-prefix checks in server/middleware as your only auth for pages. 4.6.0–4.6.2 showed they can be skipped.
  • The params option on $fetch/useFetch. Use query, since Nuxt 5 drops the alias.
  • Hand-augmenting InternalApi. Use ServerRoutes from @nuxt/schema.
  • Mixins in new code. The docs say they're kept "only for migration and familiarity reasons".
  • Running nuxt dev --host on café or office Wi-Fi without a configured secret.

Real problem solved

End Point Dev: Vue 2 → Vue 3 with a "carefully directed" AI agent

Who
Kevin Campusano at End Point Dev (15 Oct 2026), working on a client's legacy B2B e-commerce app. Customers log in, filter a catalogue, use a cart and place orders that go to an external fulfilment system.
Problem
A Vue 2 front end on Rails 5 with Webpacker, both deprecated, had to move to Vue 3 and Vite as part of a Rails 5 → 8 upgrade. There were very few automated tests, and the team wanted to keep understanding and owning the code, not hand it all to an agent.
Approach
They audited what had to change (Vuex, Vue Router, an Event Bus, Vue filters, Spraypaint, Action Cable, Foundation) and chose Pinia, Mitt and Vite. Next they wrote Capybara end-to-end tests: a few by hand, then more from the agent following those patterns. They hand-ported the layout, header and home view as the reference. Then they wrote a MIGRATION_GUIDE.md (decisions and target design) and a MIGRATION_PLAN.md (a checklist of vertical slices). The agent (GitHub Copilot as the harness) worked through the plan one step at a time, with the old code in a reference folder, permission to run tests, the app and Playwright, and a human review after every step.
Result
The migration finished, and the Capybara tests "translated pretty cleanly and passed without too many complications". There are no published speed or time numbers. The agent still made mistakes and drifted from conventions, and the guide and plan needed several revisions. In the author's words, "there are no free lunches".
Takeaway
Agents shine on "well specified projects with clear success criteria". Write the tests and one hand-ported example first, keep the decisions in a document you own, and review small slices. The same recipe fits a Nuxt 4 → 5 move with compatibilityVersion: 5, or turning on routeTypedFetch across a codebase.

VueMid → SeniorComposables · reactivity · reuse
Why did Vue move from mixins to composables? Then write a useOrder(id) composable that works whether the caller passes a plain id, a ref, or () => route.params.id, and refetches from the Spring API when it changes.

Asked in: GreatFrontEnd's Senior Vue.js guide ("How do composables differ from the old mixins pattern, and why did Vue move away from mixins?"), GreatFrontEnd's 2026 Vue guide (Q18 "What is a composable?"), and Hyring's Vue set (Q23 "What is a composable, and how do you write one?" and, for Experienced, Q47 "How do you design composables that scale across a codebase?").

What they're really testing

  • Can you name the three concrete problems with mixins, not just say "composables are newer"?
  • Do you understand reactivity across a function boundary: toValue() inside a watcher, returning refs, and cleaning up side effects?
Show model answer

30-second version: the docs list three mixin drawbacks: an unclear source of properties, namespace collisions, and implicit cross-mixin communication through shared keys. Composables fix all three because they're plain functions with explicit inputs and outputs. To accept any input shape, type it as MaybeRefOrGetter and normalize it with toValue() (3.3+) inside a watcher so the dependency is tracked. Return a plain object of refs so callers can destructure, and cancel the in-flight request when the id changes or the component unmounts.

composables/useOrder.ts
import { ref, watch, toValue, onWatcherCleanup, type MaybeRefOrGetter } from 'vue'

interface Order { id: string; status: string; total: number }

export function useOrder(id: MaybeRefOrGetter<string>) {
  const order = ref<Order | null>(null)
  const error = ref<Error | null>(null)
  const loading = ref(false)

  watch(() => toValue(id), async (orderId) => {
    const ctrl = new AbortController()
    onWatcherCleanup(() => ctrl.abort())          // sync, before any await
    loading.value = true; error.value = null
    try {
      const res = await fetch(`/api/orders/${encodeURIComponent(orderId)}`, { signal: ctrl.signal })
      if (!res.ok) throw new Error(`HTTP ${res.status}`)
      order.value = await res.json()
    } catch (e) {
      if (!ctrl.signal.aborted) error.value = e as Error
    } finally {
      if (!ctrl.signal.aborted) loading.value = false
    }
  }, { immediate: true })

  return { order, error, loading }               // plain object of refs
}

// usage: all three work
// useOrder('64f1c0…') · useOrder(selectedId) · useOrder(() => route.params.id as string)
Junior answer"Composables are the Composition API version of mixins." Writes const value = unref(id) at the top of the function, so the getter is read once and the composable never refetches. Returns reactive({ order, loading }), which callers then destructure.
Senior answerNames the three mixin problems. Tracks the input through toValue in the watch source, returns refs, and handles races and cleanup with onWatcherCleanup. Keeps the composable focused on one concern. Hyring warns that one doing too much is "just a mixin with new syntax". In Nuxt, would use useFetch with a getter URL instead, for SSR payload transfer.

Likely follow-ups

  1. Why return refs instead of a reactive object? (The docs: destructuring a reactive object makes callers "lose the reactivity connection", while refs keep it.)
  2. Can you call useOrder inside a click handler or after an await? (Composables must be called synchronously in <script setup> or setup(). The one exception is that <script setup> may call them after await.)
  3. When would you choose a renderless component instead? (When you're reusing logic and visual layout. For pure logic, the docs prefer composables because they "do not incur the extra component instance overhead".)

Common mistake: calling toValue(id) once outside the watcher. The docs stress that it must be called "inside the watchEffect callback" (or the watch source) so the dependencies it reads are tracked. Otherwise the composable silently shows the first order forever.

NuxtSeniorMiddleware · auth · security
How would you protect /account/** in a Nuxt app backed by a Spring API? Explain route middleware vs server/middleware, and where the check that really matters lives.

Asked in: GoodSpace's Nuxt set (Q27 "What is the difference between route middleware and server/middleware/ in Nuxt 3?", Q21 "How do you implement authentication in a Nuxt 3 app?"), Index.dev's Nuxt guide ("Describe Nuxt 3's middleware execution order and how to implement complex authentication flows with route guards", and the coding task "Implement a middleware… that checks user authentication and redirects to login"), Climb the Ladder (Q3, Q6) and Hyring's Nuxt.js set (Q6 on middleware).

What they're really testing

  • Do you know the two middleware systems: where each runs, when, and what it's allowed to return?
  • Do you treat front-end checks as UX and put authorization on the server, where it can't be bypassed?
Show model answer

30-second version: route middleware (app/middleware) runs "within the Vue part" of the app. For the first page it runs during SSR and "then again on the client", and after that on every client navigation. It redirects by returning navigateTo() or blocks with abortNavigation(). server/middleware handlers "run on every request before any other server route" and "should not return anything". They only add to event.context or throw. Neither is the real lock. Spring Security must authorize every /api/** call, and Nuxt server routes must check the session themselves. Nuxt 4.6.3 showed why: on 4.6.0–4.6.2, /%2e/admin rendered a page while skipping path-based server middleware.

app/middleware/auth.ts · app/pages/account/index.vue
// app/middleware/auth.ts: UX only; Spring still rejects bad tokens
export default defineNuxtRouteMiddleware((to) => {
  const user = useState<{ id: string } | null>('user')   // filled by a plugin from /api/me
  if (!user.value && to.path !== '/login') {          // avoid an infinite redirect loop
    return navigateTo({ path: '/login', query: { redirect: to.fullPath } })
  }
})

// app/pages/account/index.vue
<script setup lang="ts">
definePageMeta({ middleware: ['auth'] })
const { data: profile } = await useFetch('/api/me')   // the server route checks the session again
</script>
Junior answer"Add an auth middleware that redirects to /login." They don't mention that it also runs on the server, don't check to.path (which risks a redirect loop), and assume the page is now secure.
Senior answerSeparates UX gating (route middleware) from enforcement (Spring Security and session checks in Nuxt server routes). Knows global middleware runs first, alphabetically (control it with 01. prefixes), followed by page middleware in array order. Uses .global sparingly. Mentions that redirect route rules "are not an access control mechanism", and keeps Nuxt patched.

Likely follow-ups

  1. Why does my middleware log twice on a hard refresh? (It runs during SSR and again on the client. To skip the client run on first load, return early when import.meta.client && nuxtApp.isHydrating && nuxtApp.payload.serverRendered.)
  2. Can a server/middleware handler send a 401? (It shouldn't return a response. It can throw createError({ status: 401 }), or set event.context.user and let each route decide.)
  3. How do you add middleware from a module or plugin? (addRouteMiddleware(name, fn, { global: true }) in a plugin. A named one overrides any existing middleware with the same name.)

Common mistake: treating route middleware or a redirect route rule as the security boundary. The page's data endpoints stay reachable directly. If /api/me and the Spring endpoints don't check auth themselves, anyone with curl can read the data.
