Must-have this week

If you only take three things

  1. Before you upgrade to Nuxt 4.6 with npx nuxt upgrade --dedupe, check your Node version. The 4.6 upgrade notes list ^22.22.3 || ^24.15.0 || >=26.0.0, so CI images still on Node 20 (or an older Node 22) will fail.
  2. Make sure the Vite in your lockfile is at least 8.3.3, 7.3.7 or 6.4.4. On 6 October, Vite patched three dev-server advisories across five release lines. Run npm ls vite, and be extra careful if you use nuxt dev --host on a shared network.
  3. Search your composables for ref() or reactive() at module scope. On the server, that state is shared by every request, so one user's data can show up for another. Move it into useState or a Pinia store. The Vue interview question below explains why.

Nuxt 4.6Stable

useFetch addons with defineUseFetchAddon

From the docs: an addon is "a reusable extension for useFetch composables created with createUseFetch". It "can declare custom call-site options, wrap the handler with middleware, attach custom logic or extend the returned object". Before this, the same logic got copied into every useFetch call or hidden in a wrapper that lost its typing.

1 · DefinedefineUseFetchAddon({ setup }). setup runs on every call and gets the merged options
2 · AttachPass it to createUseFetch({ addons: [...] }), exported from composables/
3 · CalluseSpring('/api/orders', { csrf: false }). Custom options and extra return values are typed

Turn it on

app/composables/useSpring.ts
// Nuxt 4.6+. One place for every Spring Boot rule.
export const spring = defineUseFetchAddon({
  setup: (options: UseFetchAddonOptions<{ csrf?: boolean }>) => {
    // setup runs at the call site, so composables work here
    const config = useRuntimeConfig()
    const xsrf = useCookie('XSRF-TOKEN')                // CookieCsrfTokenRepository
    const { cookie } = useRequestHeaders(['cookie'])   // SSR only, {} in the browser

    options.baseURL ??= config.public.apiBase
    options.credentials ??= 'include'
    options.csrf ??= true

    options.onRequest.push(({ options: req }) => {   // always an array
      if (import.meta.server && cookie) req.headers.set('cookie', cookie)
      const method = (req.method ?? 'GET').toUpperCase()
      if (options.csrf && xsrf.value && !['GET', 'HEAD', 'OPTIONS'].includes(method)) {
        req.headers.set('X-XSRF-TOKEN', xsrf.value)
      }
    })
  },
})

export const useSpring = createUseFetch({ addons: [spring] })

// in a page
const { data: me } = await useSpring<Me>('/api/users/me')
await useSpring('/api/public/ping', { csrf: false })   // typed custom option

Watch out for

  • createUseFetch "is a compiler macro". It must be an exported declaration in composables/ or another scanned directory.
  • Custom options are "not part of the auto-generated key by default". If an option changes the response (a tenant, a scope), add a key resolver, and declare setup before key so TypeScript infers the options.
  • Addons run in array order, and the first addon's middleware is the outermost wrapper. Listing the same addon twice runs it once.
  • Custom options are passed to $fetch too, which ignores keys it doesn't recognise. Don't give one the same name as a real fetch option.

In your project: Spring Security's cookie-based CSRF (CookieCsrfTokenRepository) expects the XSRF-TOKEN cookie to come back as an X-XSRF-TOKEN header on every unsafe method. The SSR cookie forwarding from Snippet 2 two weeks ago lives in the same addon now, so pages just call useSpring(). If you use Spring's JWT resource server instead, swap the CSRF branch for the docs' Authorization: Bearer example.

Official docs: defineUseFetchAddon · createUseFetch
Vue 3.6 RCPre-release

Vapor Mode, now usable from Nuxt

Vapor is "an alternative compilation strategy introduced in Vue 3.6 that renders components without the Virtual DOM, lowering memory use and improving runtime performance". Vue's 3.6.0-rc.1 notes call it feature-complete and recommend it for parts of existing apps or for small new apps. vuejs.org doesn't have a guide page for it yet, so this section is based on the official GitHub release notes and nuxt.com's Vapor section.

1 · InstallInstall vue@^3.6.0-rc.2 or later (rc.11 is current), then set vue.vapor: true in Nuxt or use vaporInteropPlugin in plain Vue
2 · Opt inAdd vapor to <script setup>. It works per component or per page
3 · MixThe app root stays on the VDOM. Vapor and VDOM components pass props, events and slots to each other

Turn it on

nuxt.config.ts · app/components/OrderRow.vue
// nuxt.config.ts (Nuxt 4.6+). Installs Vue's vaporInteropPlugin
export default defineNuxtConfig({
  vue: { vapor: true },
})

// plain Vue app instead:
// createApp(App).use(vaporInteropPlugin).mount('#app')

<!-- app/components/OrderRow.vue: a hot, simple list row -->
<script setup vapor lang="ts">
const { order } = defineProps<{ order: { id: string; status: string; total: number } }>()
const emit = defineEmits<{ select: [id: string] }>()
const total = computed(() => order.total.toFixed(2))
</script>

<template>
  <tr @click="emit('select', order.id)">
    <td>{{ order.id }}</td><td>{{ order.status }}</td><td>{{ total }}</td>
  </tr>
</template>

Watch out for

  • It's still a release candidate (3.6.0-rc.11), and Nuxt marks Vapor support "experimental … The API may change". Nuxt recommends "trying Vapor Mode in a fresh project rather than adding it to an existing one".
  • Not supported in Vapor components: the Options API, app.config.globalProperties, v-memo and @vue:xxx events. getCurrentInstance() returns null, and template refs don't expose $el.
  • The Nuxt-specific limits: full Vapor apps aren't supported; <ClientOnly>, <NuxtIsland> and <Title>-style head components can't read Vapor slot content; and Nuxt composables called after an await "may lose the Nuxt context".
  • The release notes say mixed nesting has "rough edges", especially with VDOM component libraries, and recommend keeping separate regions for each mode. Since rc.2, event delegation is opt-in through the .delegate modifier.

In your project: good candidates are large read-only lists of Spring data, such as an orders table with hundreds of rows from a Page<Order>. Each row is a small Composition API component. Keep forms and anything built on Vuetify or PrimeVue on the VDOM for now. Try it on a branch, profile before and after, and don't ship an RC to production.

Official docs: Nuxt → Vue.js Development → Vapor Mode · Vue 3.6.0-rc.1 release notes (About Vapor Mode)

Announce Spring save results to screen readers Basic · Nuxt 4.4.2+

A toast is invisible to screen-reader users. useAnnouncer writes to a hidden live region. Add <NuxtAnnouncer /> once and call it from anywhere.

app/app.vue · app/components/SaveAddress.vue
<!-- app.vue: mount the live region once -->
<template>
  <NuxtRouteAnnouncer />
  <NuxtAnnouncer />
  <NuxtPage />
</template>

<!-- SaveAddress.vue -->
<script setup lang="ts">
const { polite, assertive } = useAnnouncer()
const form = reactive({ street: '', city: '' })

async function save() {
  try {
    await $fetch('/api/addresses', { method: 'POST', body: form })
    polite('Address saved')                         // waits for the reader to finish
  } catch (e: any) {
    // Spring ProblemDetail → { title, detail, status }
    assertive(`Could not save: ${e?.data?.detail ?? 'please try again'}`)   // interrupts
  }
}
</script>

Rule of thumb from the docs: use polite for updates that can wait (saved, loaded, "found 12 results") and assertive only for urgent ones like errors. <NuxtRouteAnnouncer> handles page changes, and <NuxtAnnouncer> handles in-page updates.

Type your Spring Boot endpoints without a codegen step Intermediate · Nuxt 4.6+

Pass routes to createUseFetch, and the response, query and body are typed for each path and method. It reuses the spring addon from the spotlight for the base URL and CSRF.

app/composables/useOrdersApi.ts
import type { DynamicParam, Endpoint } from 'nuxt/app'
import { spring } from './useSpring'

type Status = 'PENDING' | 'PAID' | 'SHIPPED' | 'CANCELLED'   // mirrors the Java enum
interface Order { id: string; status: Status; total: number; createdAt: string }
interface Page<T> {                        // Spring Data PagedModel JSON
  content: T[]
  page: { size: number; number: number; totalElements: number; totalPages: number }
}

interface OrderRoutes {
  '/api/orders': {
    [Endpoint]: {
      GET:  { response: Page<Order>, query: { page?: number; size?: number; sort?: string } }
      POST: { response: Order, body: { customerId: string; items: { sku: string; qty: number }[] } }
    }
    [DynamicParam]: {                          // /api/orders/{id}
      [Endpoint]: { GET: { response: Order } }
    }
  }
}

export const useOrdersApi = createUseFetch({
  routes: {} as OrderRoutes,                  // type only, dropped at runtime
  addons: [spring],
})

// page:  const { data } = await useOrdersApi('/api/orders', { query: { page: 0, size: 20 } })
//        data.value?.content[0].status  → Status
//        await useOrdersApi('/api/orders', { method: 'post', body: { customerId, items } })

Gotchas from the docs: paths are matched "as written", so don't add the baseURL to them. A path built at runtime resolves to unknown. Unknown paths are allowed unless you enable experimental.routeTypedFetch + strictRouteTypes. If you already publish an OpenAPI spec with springdoc, fetchdts's compileRoutes can generate this interface for you. Java Instant/LocalDate arrive as JSON strings, so type them as string.

A portable BFF route that validates before Spring sees it Advanced · Nuxt 4.6+ · nuxt/server

Import from nuxt/server so the handler keeps working on Nitro 2, on Nitro 3 in Nuxt 5, and on the Vite server builder. Bad input gets a 400 response before it reaches your Java service.

server/api/orders.post.ts
import { defineEventHandler, readValidatedBody, getRequestHeader,
         useRuntimeConfig, createError } from 'nuxt/server'   // explicit, NOT auto-imported
import { z } from 'zod'

const NewOrder = z.object({
  customerId: z.string().min(1),
  items: z.array(z.object({ sku: z.string(), qty: z.number().int().positive() })).min(1),
})

export default defineEventHandler(async (event) => {
  // any Standard Schema works; invalid → 400 with data.issues
  const order = await readValidatedBody(event, NewOrder)
  const { springApiBase } = useRuntimeConfig()   // private key; no per-request form

  // global $fetch isn't part of nuxt/server: use fetch and check ok yourself
  const res = await fetch(`${springApiBase}/api/orders`, {
    method: 'POST',
    headers: {
      'content-type': 'application/json',
      cookie: getRequestHeader(event, 'cookie') ?? '',   // forward the session only
    },
    body: JSON.stringify(order),
  })
  if (!res.ok) {
    throw createError({ status: res.status, statusText: 'Order service rejected the request' })
  }
  return (await res.json()) as { id: string; status: string }   // annotate the value → typed $fetch
})

Why it matters: on Nuxt 4, the auto-imported defineEventHandler, readBody and similar are still h3's helpers, and mixing them with nuxt/server raises NUXT_E8012. Other differences from h3 v1: createError takes status/statusText, and plain fetch doesn't throw on a non-2xx status. Keep springApiBase under top-level runtimeConfig (env NUXT_SPRING_API_BASE) so it never reaches the browser.

Tips & tricks

Small things that save time

Learn the new nuxt dev shortcutsCLI v4 shows a terminal panel: r restarts, o opens the app, l shows logs, n shows requests, and p lists pages and server routes. Use --no-tui for the classic output, for example in Docker logs.
Search the docs for your Nuxt versionnuxt docs "useFetch serialize" searches the docs that match your installed version, so you don't land on 3.x pages by accident.
Keep big Spring DTOs out of the payloadIn development, 4.6 warns when a page's payload is over 100 kB. Use pick to keep only the fields you render, or serialize: false (v4.6) to leave server-fetched data out of __NUXT_DATA__. With serialize: false, the client refetches after hydration.
Sliding cookie expiry is one line nowuseCookie('token', { expires: () => new Date(Date.now() + 3600_000) }). The getter is re-evaluated on every write, so assigning a new value also extends the cookie. Keep the getter pure.
Order global middleware with number prefixesGlobal middleware runs in alphabetical order by filename, compared as strings, so 10.x.global.ts sorts before 2.y.global.ts. The docs suggest 01., 02. prefixes.

Best practices & industry practices

What teams are standardising on

Based on the Nuxt 4.6 release and upgrade guide, the server-imports and state-management docs, and Vue's composables guide.

Do

  • In new server routes, import server helpers from nuxt/server explicitly. You won't need to migrate them for Nuxt 5.
  • Set NUXT_APP_SECRET (32+ chars, e.g. openssl rand -base64 32) in every deployed environment. "Builds never generate one."
  • Keep per-user state in useState or Pinia, never in a module-scope ref.
  • Treat route middleware as UX. Spring Security still checks every API call.
  • Put base URL, credentials and CSRF handling in one createUseFetch addon instead of repeating them on every call.

Retire

  • nuxt init. It's removed in CLI v4; use npm create nuxt@latest.
  • Mixins. The Vue docs say "we no longer recommend using mixins in Vue 3"; use composables.
  • createError({ statusCode, statusMessage }) in nuxt/server code. Use { status, statusText }.
  • Node 20 CI images, and Node 22 below 22.22.3, for Nuxt 4.6 projects.
  • Running Nuxt 3. It reached end of life on 31 July 2026, and there's no 3.x release alongside 4.6.

// nuxt.config.ts
export default defineNuxtConfig({
  runtimeConfig: {
    springApiBase: 'http://localhost:8080',          // server only · NUXT_SPRING_API_BASE

    routeTypedFetch: true,     // opt-in on 4.x, default in Nuxt 5 (Date → string at call sites)
  },

Real problem solved

Fintech rewrite: ~300k lines from Nuxt 2 to Nuxt 3, without freezing features

Who
Cowrywise, a Nigerian fund manager licensed by the SEC, with savings, investment and mutual-fund products. The work was on its largest web app.
Problem
They wanted Vue 3's logic reuse, better performance and TypeScript. The official automatic upgrade path failed on a 296,554-line codebase, because of library incompatibilities, Node version conflicts and dependencies that only supported Vue 2.
Approach
They started a fresh Nuxt 3 project (TypeScript, ESLint, Prettier). They mapped global pieces (plugins, stores, middleware, layouts) and local pieces (pages, components), then migrated from the least-coupled piece to the most, saving stores and global mixins for last so engineers could work in parallel. Mixins became composables, filters became utility functions and requests moved to $fetch. Because the automated tests weren't reliable, migrated flows got multi-engineer manual and exploratory testing. In "catch-up mode", new features shipped in the old app and were rebuilt in the new one until they could launch.
Result
It launched in production. The team describes the result as "faster, more maintainable, future-proof", then did a post-launch cleanup of packages, types and rushed code. The post gives no performance numbers, so neither do we.
Takeaway
For a large app, a planned rewrite in dependency order can be more predictable than forcing the automatic migration. Building every feature twice is the expensive part, so plan a feature freeze or release windows. This is relevant now: Nuxt 3 reached end of life on 31 July, and the same dependency-mapping approach works for a 3 → 4.6 move. (The post is from January 2026.)

Interview corner

One Vue question, one Nuxt question

This week's topics are composables and state, and middleware and auth. Answer out loud first, then open the model answer. The answers were checked against vuejs.org and nuxt.com.

VueMid → SeniorComposables · shared state · SSR
You extract a useCart() composable. A teammate moves const items = ref([]) above the function "so every component shares the cart". It works locally, but in production SSR some users see someone else's cart. Why? And how would you choose between a plain composable, useState and Pinia?

Asked in: GreatFrontEnd's 2026 Vue guide ("What is a composable?" for freshers; "How do you choose between props, provide/inject, and Pinia?" for seniors), the softwaredeveloperhub01 Vue Q&A list on GitHub (Q36 "What are composables?", Q47 on mixins, Q92 "How do you reuse logic without mixins?") and SecondTalent's Nuxt hiring guide (Q9, useState vs Pinia). The SSR leak follow-up comes from Vue Mastery's "Pinia vs useState" article on cross-request state pollution.

What they're really testing

  • Do you know that state created inside a composable is per call, while state at module scope is a singleton?
  • Do you understand how SSR module lifetimes cause cross-request state pollution, and which tool gives you per-request state?
Show model answer

30-second version: refs created inside a composable are new on every call, so each component gets its own copy. Moving the ref to module scope makes it a singleton. In the browser that's fine, because modules are "initialized fresh for each browser page visit". On the server, though, modules are initialized once at boot and "reused across multiple server requests", so one user's cart leaks into another user's render. The Vue docs call this cross-request state pollution. The fix is per-request state. In Nuxt, use useState('cart', …), which is keyed, created per request and serialized to the payload. When the logic grows (actions, devtools, HMR, team conventions), use a Pinia store; @pinia/nuxt creates it per request. Keep plain composables for logic that is per component instance.

app/composables/useCart.ts
// ❌ module scope: one array for the whole server process
const items = ref<CartItem[]>([])
export function useCartBad() { return { items } }

// ✅ per-instance logic: fresh state on every call
export function useQuantity(initial = 1) {
  const qty = ref(initial)
  return { qty, inc: () => qty.value++ }       // plain object of refs
}

// ✅ shared + SSR-safe in Nuxt: keyed, per request, serialized
export const useCart = () => {
  const items = useState<CartItem[]>('cart', () => [])
  const total = computed(() => items.value.reduce((s, i) => s + i.price * i.qty, 0))
  return { items, total, add: (i: CartItem) => items.value.push(i) }
}

// ✅ bigger domain logic: Pinia setup store (one per request with @pinia/nuxt)
export const useCartStore = defineStore('cart', () => {
  const items = ref<CartItem[]>([])            // fine here: scoped to the pinia instance
  async function load() { items.value = await $fetch<CartItem[]>('/api/cart') }
  return { items, load }
})
Junior answer"Composables share logic, Pinia shares state." They try a reactive() at module scope, see it work in the browser, and can't explain why SSR leaks.
Senior answerExplains per-call vs module-scope lifetimes and how server modules are reused, and names cross-request state pollution. Picks useState for small, serializable shared state and Pinia for domain stores, and points out that useState values must be JSON-serializable (no classes, functions or symbols). Mentions the Nuxt docs' warning: "Never define const state = ref() outside of <script setup> or setup()".

Likely follow-ups

  1. Why return an object of refs instead of a reactive()? (So callers can destructure without losing reactivity. Destructuring a reactive object breaks the connection.)
  2. Can you call a composable inside setTimeout or after an await? (Call composables synchronously in setup. <script setup> is the only place you can call them after await, because the compiler restores the instance.)
  3. Why composables over mixins? (The docs list three reasons: you can't tell where a property comes from, keys collide between mixins, and mixins are implicitly coupled through shared keys. Composables fix all three.)

Common mistake: "it works in dev, so it's fine." The leak only appears when concurrent SSR requests hit the same server process, which is exactly what you get in production and rarely while testing alone on localhost.

Official docs: SSR → Cross-request state pollution · Composables · Nuxt state management
NuxtMidMiddleware · plugins · auth
The /account/** pages need a logged-in user, and authentication lives in Spring Security (a JSESSIONID session). Where do you put the check: route middleware, server middleware or a plugin? And what does each one actually protect?

Asked in: ClimbTheLadder's Nuxt set (#3 "Describe how middleware works in Nuxt…", #6 "How do you implement authentication in a Nuxt application?"), SecondTalent's Nuxt hiring guide (Q13 on middleware, Q16 on JWT/sessions and protecting routes with middleware, Q10 on plugins) and Hyring's Nuxt.js set (Q6 "How would you explain middleware in a Nuxt.js interview?").

What they're really testing

  • Can you tell the Vue-side route middleware apart from Nitro server middleware and plugins, and do you know when each one runs?
  • Do you know that client-reachable checks are UX, and the real security boundary is on the server, which here means Spring?
Show model answer

30-second version: a plugin runs when the app initializes. Use it to load the current user once (GET /api/users/me with the forwarded cookie) into useState. Route middleware (defineNuxtRouteMiddleware) "run within the Vue part" of the app before navigation, on the server for the first render and again in the browser. It reads that state and returns navigateTo('/login'), which becomes a 302 on the server. Server middleware (server/middleware) runs on every request to Nitro before server routes. It should only inspect or extend event.context or throw, and it only guards Nuxt's own server/api routes. None of these protect Spring's data, so Spring Security has to check every endpoint. As the Nuxt docs put it, "Client-side middleware is helpful for the user, but without server-side protection your data can still be accessed."

app/plugins/01.session.ts · app/middleware/auth.ts · pages/account/index.vue
// app/plugins/01.session.ts: load the user once (server render, then hydrated)
export default defineNuxtPlugin(async () => {
  const user = useState<Me | null>('me', () => null)
  if (user.value) return                         // already in the SSR payload
  user.value = await $fetch<Me>('/api/users/me', {
    baseURL: useRuntimeConfig().public.apiBase,
    headers: useRequestHeaders(['cookie']),
    credentials: 'include',
  }).catch(() => null)                           // 401 → anonymous
})

// app/middleware/auth.ts: named middleware, a UX redirect only
export default defineNuxtRouteMiddleware((to) => {   // use `to`, never useRoute()
  const user = useState<Me | null>('me')
  if (!user.value && to.path !== '/login') {
    return navigateTo({ path: '/login', query: { redirect: to.fullPath } })
  }
})

// app/pages/account/index.vue
definePageMeta({ middleware: 'auth' })
Junior answer"Put a middleware on the page that checks a token." They don't separate route middleware from server middleware, and they don't mention that the API still has to check every request.
Senior answerGives a role to each of the three. Knows route middleware runs on the server and again on the client, and that redirects are made by returning navigateTo/abortNavigation, not by calling next(). Guards against redirect loops. Uses to instead of useRoute(). Says Spring Security enforces access on every endpoint and that server middleware only matters if Nuxt has its own BFF routes.

Likely follow-ups

  1. The middleware runs twice on first load. How do you skip the client run? (Check import.meta.client && nuxtApp.isHydrating && nuxtApp.payload.serverRendered and return early.)
  2. Why not call useRoute() inside middleware? ("There is no concept of a 'current route' in middleware", because it can redirect or abort. Use the to/from arguments.)
  3. How do you run auth on every route except a few? (Name the file auth.global.ts and allowlist public paths, or use the appMiddleware route rule to turn middleware on or off by path.)

Common mistake: treating route middleware as the security boundary. It runs in code the browser downloads and can be bypassed by calling the API directly. A second, smaller mistake: redirecting to /login without checking to.path, which the docs warn "might get an infinite redirect loop".
